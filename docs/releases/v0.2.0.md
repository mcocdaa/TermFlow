# TermFlow v0.2.0 release notes (draft)

> Status: draft and not release-ready. Do not publish or tag until the
> remaining real-container and live-model gates in the Agent Broker
> implementation plan are recorded.

## Highlights

- Adds the first-party Agent Broker to Control Plane B, with durable
  conversations, messages, runs, canonical timeline events, and cleanup
  tombstones.
- Adds `output_contains`, `output_idle`, and `pane_exited` watches that resume
  an Agent conversation through durable Inbox delivery. The optional shell
  marker design is not part of v0.2.0 and Computer A is not modified.
- Adds human-in-the-loop terminal write approvals with exact argument hashes,
  single-use decisions, expiry/revocation handling, audit records, and
  fail-closed recovery for uncertain execution outcomes.
- Adds authenticated Agent Chat and replayable Agent event streams to the Web
  and Tauri clients. Tauri keeps transport and DPoP signing in Rust rather
  than granting new WebView network authority.
- Adds the pinned OpenCode reference backend deployment, authenticated health
  gating, deny-by-default tool configuration, epoch-bound TermFlow MCP
  credentials, and isolated container defaults.

## Security and scope boundaries

- A reference OpenCode runtime belongs to one Agent binding. Same-binding
  conversations are serialized; revoke or profile reconfiguration advances
  the runtime epoch and invalidates prior capabilities.
- An ordinary B restart does not rotate the epoch. Runtime admission requires
  an authenticated, structurally valid OpenCode `/global/health` response.
- The current live overlay uses the provider-specific `DEEPSEEK_API_KEY` only
  inside OpenCode; the pinned binary does not consume a generic
  `OPENCODE_MODEL_API_KEY`. B receives disclosure metadata, never the provider
  secret.
- OpenCode has no Docker socket, host terminal filesystem, public host port,
  or direct Computer A connection. Terminal reads and writes pass through B's
  scoped MCP and approval policy.
- Voice/STT and unlimited autonomous terminal writes are not v0.2.0
  capabilities.

### Disposable live-model evidence (2026-09-02)

This is deployment evidence for one disposable Compose project, not a general
provider guarantee.  DeepSeek `GET /models` returned HTTP 200 and included the
configured `deepseek-v4-flash` model; a direct chat-completions probe also
returned HTTP 200 with a reviewed tool call.  The combined B/OpenCode/MCP run
used the pinned OpenCode `1.18.18` image and a custom DeepSeek provider.

- Node A was online with one pane (`%0`); B admitted the prompt with HTTP 202.
- OpenCode exposed the namespaced MCP tool
  `termflow_termflow_list_panes` and executed it exactly once.
- MCP returned the pane list containing `%0`; B persisted `tool_started` and
  `tool_completed`, then persisted the final assistant body `%0`.
- B's canonical event payloads contained only bounded tool identity/status;
  tool input and output were not retained.  Current OpenCode
  `session.status`/`session.idle`, `message.part.delta`, and tool-part events
  are now normalized by the adapter.
- A second disposable run exercised the write path.  B created an approval
  with a 64-character canonical arguments hash before any pane input; one
  admin approval moved it to `consumed`, the pane contained the probe text,
  and a duplicate decision returned HTTP 409.  Timeline replay returned the
  next event after a saved cursor, and conversation deletion returned 204 with
  a completed cleanup tombstone.

The live read/write, approval, receipt, replay, and deletion paths passed for
those disposable runs. Revocation/stale-token closure, disconnect recovery
during a model turn, and OpenCode `once`/`reject` interaction remain
unverified release gates for the real provider deployment.
