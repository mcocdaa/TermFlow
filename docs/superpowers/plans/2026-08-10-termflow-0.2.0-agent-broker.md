# TermFlow 0.2.0 Agent Broker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Status:** Discussion draft. Do not execute this plan until the decisions in “Discussion Gates” are reviewed and this status is changed to approved.

**Goal:** Turn Control Plane B into a terminal capability broker, durable event broker, and agent gateway. TermFlow users can converse with an externally deployed agent, let it observe multiple remote panes, register durable continuations, and perform policy-gated terminal actions.

**Architecture:** Agent Broker is a trusted, first-party Feature Plugin inside B. OpenCode is its first reference backend and runs in a separate Docker container. B's kernel owns authentication, Terms, bridge connections, lifecycle, and core ports; the Agent Broker plugin owns product conversations, the durable Agent Inbox, canonical agent events, watches, approvals, audit, and terminal tool authorization. OpenCode consumes typed inputs through a backend plugin/adapter, calls B's terminal tools through MCP, and returns backend events through its HTTP/SSE API. Backend-specific session IDs and event shapes do not leak outside the plugin boundary.

**Tech Stack:** Python 3.12, FastAPI, Pydantic, SQLite/aiosqlite/Alembic, asyncio, the official MCP Python SDK, OpenCode Server HTTP/SSE, Vue 3, existing Web/Tauri client runtime ports, tmux control mode and `capture-pane`, optional STT provider container.

---

## 1. Why This Replaces the Previous Plan

The previous version had useful product intent but was not safe to execute. This revision fixes these blockers:

- The current Alembic head is `0005`; Agent Broker starts at `0006`, not another `0002`.
- Agent Broker is a B Feature Plugin, not a second control-plane application and not an arbitrary user-uploaded Python extension. Its routes, services, migrations, event handlers, and lifecycle tasks are registered through a narrow B plugin contract.
- OpenCode uses its documented `/session`, `/session/:id/prompt_async`, `/event` or `/global/event`, message `parts`, and permission endpoints. There is no assumed `/session/:id/events` endpoint.
- MCP is implemented with a pinned official SDK and negotiated protocol compatibility, not a hand-written partial JSON-RPC router.
- Watches consume the existing `PANE_OUTPUT` and topology streams. They do not depend on an MCP snapshot having happened recently.
- Every pane-scoped key is `(instance_id, pane_id)`, because tmux pane IDs can repeat across Term instances.
- B stores durable inbox items and a canonical event timeline. Its existing history-free `EventHub` remains the live terminal fan-out path, not the persistence layer for agent state.
- A Term can have multiple Agent Conversations. Backend session IDs are opaque mappings, not Term IDs or product conversation IDs.
- Permission records are persistent, expiring, single-use capabilities. An in-memory generation counter is not called a lease.
- Web and Tauri use the existing client runtime transport abstraction. Shared Vue code does not open an unauthenticated WebSocket directly.
- STT, retention, external LLM disclosure, container isolation, and release versioning are explicit work rather than implicit assumptions.

The repository currently reports `0.0.1-dev.0` in Python packages. `0.2.0` in this document is a target release and requires an explicit version migration task.

## 2. Product Scope

### 2.1 Included in 0.2.0

- A first-party `agent_broker` Feature Plugin registered inside B, with explicit enable/disable configuration and lifecycle/route/migration/event registration.
- OpenCode as the first separately deployed Agent Backend.
- Backend-neutral Agent Inbox and canonical Agent Event model.
- Multiple Agent Conversations per Term.
- One controlled memory scope per `(Term, Agent Profile)` shared across its conversations.
- Product chat history and replay owned by B.
- Multi-pane observation through bounded, cursor-based tools.
- Durable watches for output text, output inactivity, and pane exit.
- Optional trusted shell integration capability for prompt/command-finished markers.
- Observe and Assisted policies.
- A documented delegated-grant design, but no unbounded delegated/autonomous write mode enabled by default.
- Agent Chat in Web and Tauri through their appropriate authenticated transports.
- Optional STT provider with transcript confirmation before submission.
- Docker Compose deployment of the OpenCode reference backend on an internal network.
- Migration, privacy, audit, recovery, compatibility, and cross-process verification.

### 2.2 Explicitly not promised in 0.2.0

- Lossless mid-conversation migration between different Agent Backends.
- An agent controlling the raw full-screen tmux client owned by C.
- Arbitrary unbounded regular-expression watches.
- Treating silence alone as proof that a command succeeded.
- Automatic modification of every user's `.bashrc` or `.zshrc`.
- Multi-instance B or a new NATS/Redis dependency.
- Persisting raw terminal streams indefinitely in B.
- Giving the OpenCode container Docker socket, A filesystem, host shell, or direct A connectivity.

## 3. Domain Language and Ownership

### 3.1 Existing product hierarchy

```text
Computer
└── Term (Instance: one private tmux server/session)
    └── Window
        └── Pane
```

The word `Session` is already overloaded by tmux and agent backends. Product APIs and storage therefore use `AgentConversation`, not a bare `AgentSession`.

### 3.2 Agent hierarchy

```text
AgentProfile
└── AgentBinding (profile attached to one Term)
    ├── AgentMemoryScope
    └── AgentConversation[]
        ├── BackendConversationRef
        ├── AgentInboxItem[]
        ├── AgentRun[]
        ├── AgentMessage[]
        ├── AgentEvent[]
        ├── ApprovalRequest[]
        └── Watch[]
```

Identity rules:

```text
term_id
!= binding_id
!= conversation_id
!= backend_conversation_id
!= agent_token_id
!= run_id
```

Only the backend adapter reads or writes `backend_conversation_id`.

### 3.3 Authority

- A owns the real tmux server, panes, topology, output, captures, and final serialized input execution.
- B owns authentication, Agent Binding, conversations, memory policy, Agent Inbox, watches, approvals, terminal tool authorization, audit, and client replay.
- C owns user interaction, recording controls, transcript confirmation, chat presentation, and approval decisions.
- OpenCode owns model inference and backend-specific context. It has no direct authority over A.
- The external model provider may receive selected terminal excerpts. B must make that disclosure visible and enforce retention/redaction policy.

### 3.4 B Feature Plugin Boundary

`agent_broker` is a trusted, versioned, first-party plugin loaded by the B composition root. It can be disabled by deployment configuration, but it is not dynamically installed from an untrusted package at runtime. It is part of B's trusted computing base; its ports are a modularity and testability boundary, not a security sandbox. The plugin receives a typed context rather than reaching into global application state:

```python
class BFeatureContext(Protocol):
    auth: AuthPort
    terms: TermPort
    observation: TerminalObservationPort
    commands: TerminalCommandPort
    persistence: UnitOfWorkFactory
    lifecycle: LifecyclePort
    runtime: AgentRuntimeSupervisor

class BFeaturePlugin(Protocol):
    id: str
    version: str

    requires_core_api: str
    def register_services(self, context: BFeatureContext): ...
    def register_routes(self, routes: FeatureRouteRegistry): ...
    def register_event_handlers(self, subscriptions: EventSubscriptionRegistry): ...
    def register_migrations(self, manifest: MigrationManifest): ...
    async def startup(self, context: BFeatureContext): ...
    async def shutdown(self): ...
```

`FeatureRouteRegistry` enforces the plugin namespace (`/api/v1/agent...`), endpoint auth/ACL/CSRF policy, and owner metadata; a plugin cannot mount an arbitrary FastAPI route. `EventSubscriptionRegistry` exposes typed, scoped subscriptions rather than the raw global EventHub. `MigrationManifest` records revision owner/dependencies for the central, static Alembic chain: disabling the feature stops routes/subscribers/workers, but does not remove already-migrated tables or skip required purge/cleanup. Import-linter and dependency tests enforce that the plugin cannot import A/tmux internals or provider-only models into the shared protocol package. A future third-party plugin would require a separate out-of-process protocol and sandbox; it is outside 0.2.0.

## 4. Four Distinct Event Families

Do not collapse these into a generic `message` or `event` model.

### 4.1 TerminalEvent: A to B

Examples:

- `pane.output`
- `stream.gap`
- `topology.changed`
- `pane.exited`
- `shell.prompt_ready`
- `shell.command_finished`

Terminal events are observations. They do not automatically invoke a model.

### 4.2 AgentInput: B to Agent Inbox

```text
AgentInput
├── UserMessage
├── WatchTriggered
├── TimerTriggered
├── PermissionResolved
└── SystemNotification
```

All inputs carry:

- `input_id`
- `conversation_id`
- `actor_id`, `actor_kind` (`user_session`, `client`, `watch_engine`, `timer`, `backend`, or `system`), and the authenticated `auth_epoch` when applicable
- `admission_seq` assigned by the B database transaction, not a client clock
- `idempotency_key` whose scope and canonical payload hash are persisted
- `source` (`user`, `system`, or `backend`) as a coarse product classification
- `kind`
- typed `payload`
- `causation_id` and `correlation_id`
- `created_at`
- delivery state and attempts

Per-conversation insertion and delivery order must be deterministic.

### 4.3 ProviderEvent: Agent Backend to Adapter

These are provider-specific OpenCode transport events consumed only inside the adapter. They are not persisted as TermFlow's public contract without normalization. Unknown backend events may be retained in a size-bounded diagnostic record, but they must not break the event pump.

Unknown events are restricted to type, provider/session/run identifiers, an error code, and hashed correlation identifiers. Raw parts, tool arguments/results, headers, SSE bodies, reasoning, and terminal excerpts are never persisted by the diagnostic path. Opt-in debugging has a short TTL, redaction, and an audited access path.

### 4.4 AgentEvent: Adapter to B and C

```text
AgentEvent
├── RunStarted
├── MessageDelta
├── MessageCompleted
├── ToolStarted
├── ToolCompleted
├── PermissionRequested
├── RunCompleted
├── RunFailed
└── BackendStateChanged
```

Every canonical event has an `event_id`, `conversation_id`, optional `run_id`, backend deduplication key, bounded payload, and B-assigned database sequence. Tool activity, permission, run-state, message-completion events, and bounded message-assembly checkpoints are durable. High-frequency `MessageDelta` frames are ephemeral live events; after reconnect C receives the latest committed assembly revision/final message, not a false promise of lossless delta replay. B persists the durable event/checkpoint before live fan-out.

## 5. Agent Backend Port

The TermFlow domain depends on this port:

```python
class AgentBackend(Protocol):
    async def capabilities(self) -> AgentBackendCapabilities: ...
    async def create_conversation(
        self, request: CreateBackendConversation
    ) -> BackendConversationRef: ...
    async def submit(
        self, ref: BackendConversationRef, request: BackendTurnRequest
    ) -> BackendSubmitResult: ...
    async def cancel(
        self, request: BackendCancelRequest
    ) -> BackendOperationResult: ...
    def events(
        self, scope: BackendEventScope
    ) -> AsyncIterator[BackendNotification]: ...
    async def reconcile(
        self, ref: BackendConversationRef
    ) -> BackendConversationSnapshot: ...
    async def interact(
        self, request: BackendInteraction
    ) -> BackendOperationResult: ...
    async def delete_conversation(
        self, ref: BackendConversationRef
    ) -> BackendOperationResult: ...
    async def close(self) -> None: ...
```

The B-only `AgentInboxEnvelope` contains actor, auth epoch, admission sequence, delivery state, attempt, and lease metadata. The adapter receives only a sanitized `BackendTurnRequest`:

```text
BackendTurnRequest
├── conversation/backend opaque refs
├── correlation_id + B idempotency key
├── typed content/parts and trust labels
├── bounded MemoryProjection / ContextBlock
└── disclosure, size, and policy metadata (never raw auth/lease state)
```

`BackendNotification` is the normalized provider-neutral event returned by a scoped adapter subscription. It contains only opaque backend refs, binding/runtime scope, normalized kind, optional run/message/part/tool IDs, stable dedup key, bounded visible payload, and `observed_at`. OpenCode `Event`, `GlobalEvent`, `Part`, `permissionID`, `directory`, reasoning, and raw provider payloads remain adapter-internal.

`BackendSubmitResult`, `BackendOperationResult`, and reconcile snapshots use explicit outcomes such as `confirmed`, `requested`, `unsupported`, `retryable`, `context_lost`, and `unknown`, with bounded evidence and retry safety. A provider operation must never be represented as `None` when B needs crash recovery.

`AgentBackendCapabilities` is an immutable negotiated descriptor, captured per binding/runtime epoch. It declares semantic modes rather than a growing list of booleans:

- streaming output
- context mode: `resume`, `fork_only`, or `lost_on_restart`
- submit mode: `idempotent`, `non_idempotent`, or `unknown`
- cancel scope: `run`, `conversation`, or `none`
- replay mode: `event`, `session`, or `none`
- concurrency mode: `serialized` or `parallel`
- tool-call identity: `binding`, `conversation`, or `run`
- runtime isolation: `binding`, `conversation`, or `tenant`
- accepted input kinds and structured-part fidelity
- tool activity events
- permission events
- usage/cost reporting
- explicit run boundaries

`events()` reconnects from the backend's live stream; it does not promise provider replay. `reconcile()` is responsible for proving message/run state after a disconnect. `submit()` reports only admission/transport acceptance; AgentRun completion comes from normalized events or reconciliation. Adding another backend means registering another trusted backend plugin/connector that implements this port and its compatibility tests. It does not require changing Watch Engine, terminal tools, Agent Chat, permissions, or product persistence.

The neutral `CreateBackendConversation` request contains only `display_title`, an opaque `BackendWorkspaceAlias`, and an optional parent conversation reference. Provider model IDs, agent names, directory query details, and routing fields stay in adapter configuration and opaque refs. `display_title` is redacted according to the disclosure policy before leaving B.

`BackendConversationRef` also records backend kind/version, runtime identity, binding capability epoch, and an opaque provider ref needed for safe reconciliation. A bare provider session ID is never sufficient to resume or authorize a call.

### 5.1 Backend switching semantics

- A new conversation may select any configured compatible backend.
- An existing conversation remains bound to its backend until closed.
- A user may fork a new conversation onto another backend using B's product transcript and memory summary.
- Backend-private reasoning, compaction state, tool state, and opaque memory are not promised to migrate.

This is replaceable-backend architecture, not magical lossless hot migration.

The plugin boundary is two-level: `agent_broker` is the B Feature Plugin; `OpenCodeAdapter` is a backend implementation selected by an Agent Profile. Adding a backend must not add routes, database tables, approval rules, or C transport code. A backend runtime may be in-process only for a trusted lightweight connector; model runtimes and provider credentials use an external process/container.

Backend tool transport is a separate connector facet:

```python
class BackendToolConnector(Protocol):
    async def attach(self, scope: BackendRuntimeScope, tools: TerminalToolPorts) -> None: ...
    async def detach(self, scope: BackendRuntimeScope) -> BackendOperationResult: ...
```

OpenCode uses MCP through this facet. A future ACP adapter may use terminal callbacks, and a native connector may use another mechanism; none of those transports become part of the Agent Broker domain contract.

## 6. OpenCode Reference Adapter

OpenCode is the first backend because it already provides a headless server, OpenAPI, asynchronous prompts, SSE, MCP, permissions, and multiple sessions.

The adapter uses the documented contract:

- `GET /global/health`
- `POST /session` with `parentID` and/or `title`; read the returned `Session.id`
- `POST /session/:id/prompt_async` with message `parts`
- one selected SSE mode recorded by the compatibility fixture: project-scoped `/event?directory=...` for an isolated runtime, or `/global/event` with the returned `directory` and persisted `Session.id` used for filtering
- `GET /session/:id/message` for reconciliation, with the same `directory` where required
- `POST /session/:id/abort`, with the same `directory` where required
- `POST /session/:id/permissions/:permissionID`, with the same `directory` where required
- `GET /session/status` and `GET /session/:id` for reconciliation, with the same `directory` where required
- `DELETE /session/:id` for idempotent backend cleanup
- `/doc` as the pinned contract fixture for adapter compatibility tests

`BackendConversationRef` persists the opaque backend session ID plus the OpenCode `directory` used to create and reconcile it. The adapter has an internal OpenCode decoder; B receives only `BackendNotification`, then creates canonical `AgentEvent` records. Resume is supported only when the runtime persistence volume and health contract prove that backend context survived restart; otherwise B marks the context lost and offers a new conversation fork from its curated transcript.

The adapter maps typed inputs as follows:

- `UserMessage`: normal user text part.
- `WatchTriggered`: a normal user-visible input part containing a structured TermFlow event whose terminal observation is explicitly marked untrusted. Terminal text is never placed in a developer/system instruction.
- `PermissionResolved`: a B approval result for a pending Agent interaction. The OpenCode permission endpoint is reached only through the adapter's optional `BackendInteraction` facet; provider permission state is never promoted into the neutral AgentInput or B terminal authority.
- `TimerTriggered` and `SystemNotification`: bounded, user-visible typed text/event parts. The adapter capability matrix must list these as accepted kinds; an unsupported kind remains queued and fails closed rather than being silently coerced.
- Unsupported input or event types fail closed and emit a canonical `RunFailed` or diagnostic event.

An OpenCode `permissionID` is opaque and stored in a single-use mapping bound to binding, backend conversation, B run, tool call, canonical argument hash, and expiry. Cross-session/replayed IDs, `always`/remember decisions, and unknown mappings are rejected. C approves only B's `ApprovalRequest`; an adapter response to OpenCode never becomes B terminal authority.

The structured representation is an interoperability encoding, not a security boundary. Terminal output, watch intent summaries, memory suggestions, and backend content are untrusted data with trust labels. B performs authorization independently of prompts, backend permissions, and model decisions. A model must never be able to turn a terminal string into a B approval or system instruction.

### 6.1 Event recovery

OpenCode SSE is an input to the adapter, not B's durable log:

1. Persist an Agent Inbox item before submitting it.
2. Claim it with a compare-and-swap owner lease and mark the submission attempt before the network call.
3. Submit with a B-generated `messageID` or equivalent stable backend key where the backend API permits.
4. Consume and normalize SSE events.
5. Persist canonical events before live fan-out.
6. On SSE disconnect, reconnect and reconcile session messages/status.
7. Deduplicate using backend event/message/part IDs plus B's run mapping.
8. If B crashes after a prompt may have been accepted but before the response is known, mark the item `delivery_unknown`. Do not automatically resubmit an action-producing turn. Reconcile by the stable message ID when possible; otherwise require an explicit user recovery decision.

The adapter must not claim exactly-once delivery when OpenCode's asynchronous endpoint only returns `204` and does not provide a transport-level idempotency key. The guarantee is “no silent duplicate action”; uncertain delivery is a visible recoverable state.

### 6.2 Runtime and MCP credential isolation

#### 6.2.1 Runtime Supervisor contract

B does not manipulate Docker or host processes directly. A deployment-owned `AgentRuntimeConnector`/`AgentRuntimeSupervisor` is a required control-plane port for any runtime that uses static MCP headers:

```python
class AgentRuntimeSupervisor(Protocol):
    async def register(self, binding_id, runtime_ref, epoch, capability_ref): ...
    async def health(self, runtime_ref) -> RuntimeHealth: ...
    async def quiesce(self, runtime_ref, deadline) -> DrainStatus: ...
    async def restart(self, runtime_ref, epoch, capability_ref) -> RuntimeHealth: ...
    async def cleanup(self, runtime_ref) -> BackendOperationResult: ...
```

The supervisor owns secret/config injection and attests the runtime's current epoch. B admits an AgentBinding only when the runtime is `ready` with the expected epoch; a second binding with no ready runtime remains disabled/fail-closed. Conversation transfer is ordered as: stop new submissions, abort/reconcile the old conversation, quiesce and drain MCP calls, rotate epoch/capability, restart or reconfigure through the supervisor, verify health/current epoch, then admit the new conversation. A drain timeout leaves the old run `unknown` and blocks activation of the new conversation. A late old-epoch tool call is rejected and recorded, never reassigned to the new run. The default Compose profile may provide a one-binding supervisor fixture; a multi-binding fleet requires an explicit external supervisor implementation.

OpenCode remote MCP configuration uses a server URL and headers, while its server-level MCP management is global or agent-profile scoped. A static shared MCP token therefore cannot safely isolate multiple Term bindings or conversations merely because they use different OpenCode session IDs.

The 0.2.0 safety default is:

- `AgentBinding` stores a reference to one externally deployed Agent Runtime endpoint and one binding-scoped MCP capability secret reference.
- Multiple `AgentConversation` records may share that runtime only when they belong to the same binding and B enforces one active Agent Run per binding.
- The active-run lease is the v0.2 tool-call attribution mechanism: a binding-scoped MCP call is accepted only while exactly one B-owned run is active for that binding. B attaches the call to that run/conversation before policy evaluation and audit. A second conversation waits in the Inbox.
- Runtime registration has a persistent `runtime_epoch`. B increments the binding/runtime epoch on B startup, binding revoke, profile change, runtime reconfiguration, or before active-run attribution transfers to another conversation, invalidating the previous static MCP capability through the supervisor. Direct OpenCode remote MCP headers cannot carry a per-run nonce; 0.2.0 therefore relies on a freshly provisioned epoch-bound binding token, strict one-active-run-per-binding serialization, side-effect request keys bound to the active run, and supervisor-controlled quiesce/restart before another conversation is admitted. A future connector may add real per-run capabilities without restarting the runtime.
- A runtime must re-register/restart with the current epoch before B accepts MCP calls after an epoch change. The adapter cancels/reconciles old runs before the next run becomes active. This is a deliberate quiesce boundary because OpenCode remote MCP headers are static for a configured server.
- A single runtime/container is not shared across bindings unless an adapter capability explicitly proves per-binding tool isolation.
- The reference Compose profile starts one OpenCode runtime for one configured binding and includes a supervisor fixture/registration contract. Supporting a fleet of per-binding containers is a deployment/orchestration follow-up, not a reason to put Docker control inside B.
- B rejects MCP calls with a missing, revoked, expired, or binding-mismatched capability. Prompt text is never used to select a Term.
- M0/M4 must run two-conversation serialized attribution and two-binding cross-call isolation tests. A passing OpenCode session test alone is insufficient.

An alternative implementation may use an isolated OpenCode subprocess per conversation behind an Agent Runtime Connector. That is compatible with the same `AgentBackend` port, but it is not the 0.2.0 direct HTTP/SSE default. OpenCode ACP currently launches `opencode acp` as a stdio subprocess; remote ACP transport is a separate bridge design, not an assumption of the HTTP adapter.

## 7. Durable Agent Inbox and Product Timeline

The Agent Inbox is the central B abstraction:

```text
C user input ─────────┐
Watch delivery ───────┼──► durable Agent Inbox ──► AgentBackend.submit()
Timer/permission ─────┘
```

Required state machine:

```text
delivery_state:
pending -> claimed -> dispatched
                    \-> retry_wait
                    \-> delivery_unknown
                    \-> dead_letter
pending/claimed/retry_wait -> cancelled
dispatched -> cancel_requested -> cancelled|unknown

run_state:
queued -> running -> completed|failed|cancelled|unknown

submission_state:
not_started -> started -> accepted|rejected|unknown
```

`dispatched` means B has submitted the item, not that the model turn has completed. Before any socket write, B commits `started` with an `attempt_id`, stable `messageID`, owner lease, and fencing token. On restart an expired claim in `started` becomes `unknown` unless reconciliation proves acceptance/rejection; only `not_started` or proven `rejected` may retry. Claims have an expiry and heartbeat for long requests. There is at most one in-flight turn per conversation unless the backend capability explicitly supports concurrency. Delivery has a bounded attempt count and a `dead_letter` state.

An item can be retried automatically only while B can prove that submission was not started or that the backend rejected the stable delivery key. If the network outcome is unknown, the durable state is `delivery_unknown`; recovery is reconciliation or an explicit user decision, never an automatic duplicate action.

Cancellation is a separate backend operation. B must call the adapter, wait for a terminal event or reconciliation, and expose `unknown` when the backend may already have started a tool or terminal action; cancellation never rolls back an A-side write. Term/conversation deletion creates a durable cleanup job and does not silently mark backend work cancelled.

B stores the product-facing timeline:

- user messages
- final agent messages and streaming assembly metadata
- visible tool activity
- approval requests and decisions
- visible system/watch events
- run state and errors

B does not need to copy private model reasoning. Raw terminal excerpts and audio are excluded from long-term persistence by default; excerpts intentionally attached to a product event use bounded retention and deletion rules.

Durable tool activity stores tool name, status, byte counts, hashes, and truncation/error metadata only. Raw read results, key sequences, write text, provider parts, and hidden reasoning are ephemeral unless the user explicitly attaches a bounded, redacted excerpt with a short TTL.

The Inbox stores only a bounded, redacted observation reference or a short-TTL excerpt for a `WatchTriggered` item. It is not an indefinite terminal transcript.

## 8. Agent Memory

`AgentMemoryScope` belongs to `(term_id, agent_profile_id)` and may be referenced by multiple conversations.

B-owned memory contains only curated product facts:

- explicit user preferences for this Term
- user-approved summaries
- references to prior conversation IDs
- bounded task state needed for durable continuations

It excludes by default:

- model hidden reasoning
- raw full scrollback
- secrets detected in terminal output
- provider credentials
- unreviewed instructions copied from terminal output

Backend context and B memory are separate:

```text
B AgentMemoryScope       portable, curated, policy-controlled
OpenCode Session         backend-specific inference context
Watch continuation       one asynchronous intent and observation cursor
```

Memory writes must record provenance (`user`, `agent suggestion`, or `system`) and allow user inspection/deletion. Agent-suggested memories are not automatically treated as trusted instructions.

Each fact also has `trust_state` (`user_approved`, `suggestion`, or `system`), source event/run, redaction status, owner/ACL, revision, expiry, and a bounded value size. A per-scope byte/count quota and optimistic CAS/unique key make concurrent writes deterministic. Only approved facts enter a model prompt. Deletion writes a tombstone and removes exported/backend copies where the configured deletion policy promises removal.

`MemoryProjection` is the only path from B memory into an Agent turn. B's assembler selects approved/system facts, bounded task summaries, and explicitly permitted references, adds trust labels and disclosure metadata, and emits a size-bounded `ContextBlock` for `BackendTurnRequest`. Agent suggestions, raw memory rows, hidden reasoning, and unapproved terminal-derived text never enter the projection. Backend adapters cannot reconstruct or widen the memory scope themselves.

## 9. Multi-Pane Observation

The agent does not need to drag a human scrollbar. It receives explicit tools over stable pane identities.

### 9.1 Existing path to reuse

```text
tmux control mode
  -> A BridgeRuntime
  -> PaneOutputBuffer (stream_id, seq)
  -> PANE_OUTPUT / STREAM_GAP
  -> B bridge and EventHub
```

A already uses `tmux capture-pane` for full pane history. Extend this as a bounded capture command instead of inventing a second terminal emulator in B.

### 9.2 Read contract

`termflow_pane_read` supports:

- `view=viewport`: rendered visible pane.
- `view=history`: bounded tmux history range or tail.
- `view=since`: raw or normalized output after a `(stream_id, seq)` cursor.
- `start_line`, `end_line`, and `tail_lines` where relevant.
- `max_bytes` enforced by A and B.
- `join_wrapped` for agent-readable logical lines.

The result includes:

- `instance_id`, `pane_id`
- content and encoding
- `stream_id`, `from_seq`, `to_seq`
- capture range and viewport geometry
- `truncated`
- explicit `stream_gap` information

Snapshots and live output have distinct semantics. A snapshot must not be appended into the live output ring as though it were new terminal output.

This requires a new correlated A/B capture request/result path, including `capture_kind` (`viewport`, `history`, `snapshot`, or `gap_snapshot`), range, `max_bytes`, pane incarnation, and a bounded result/error. It must be plumbed through `LiveConnection.pending`, the bridge receiver, and `api/bridge.py`; subscribing to the existing ephemeral EventHub is not sufficient.

### 9.3 Normalization

- Use tmux rendered capture without `-e` for ordinary agent text reads.
- Keep raw stream chunks for cursor/replay and trusted shell marker parsing.
- Do not reconstruct a terminal screen by applying a stateless ANSI-removal regex.
- Parser state must survive escape sequences split across chunks.
- Size and token-oriented truncation happen before sending context to the backend.
- `cwd` and absolute host paths are omitted/redacted by default. Exposing a normalized workspace label requires an explicit `terminal.path_observe` capability and consent; tests must reject username/repository/secret-path leakage.

## 10. Terminal Capability Service and MCP Transport

B owns backend-neutral terminal capability ports. `TerminalObservationPort` handles pane listing/read/cursor reconciliation, `TerminalCommandPort` handles serialized text/typed-key execution and receipts, and `ContinuationPort` handles durable watches. MCP is the OpenCode adapter's Agent-to-B transport facade, not the B-to-Agent wake-up protocol. A future ACP adapter or native connector may map the same ports to its callbacks without changing the domain service.

Initial tools:

1. `termflow_list_panes`
2. `termflow_pane_read`
3. `termflow_pane_send_text`
4. `termflow_pane_send_keys`
5. `termflow_watch_create`
6. `termflow_watch_list`
7. `termflow_watch_get`
8. `termflow_watch_cancel`

The tool count is not a product invariant. New tools require an explicit capability and policy review.

Rules:

- The agent token selects one Agent Binding and Term. Tools do not accept a caller-controlled `term_id`.
- Every pane lookup still uses `(instance_id, pane_id)` internally.
- Tokens contain enforced scopes, expiry, binding epoch, and revocation state.
- `pane_policies` is an execution contract: `terminal.observe` and watches use an exact pane allowlist by default; `all_panes` requires explicit Term/Binding consent. `termflow_list_panes` omits sensitive titles/cwd unless separately allowed. Every read/watch rechecks binding, pane incarnation, and policy before returning content.
- Selected content is redacted for secrets/absolute paths and bounded by byte/token quotas before provider submission. Terminal text cannot create a wider pane scope or become a system/user-approved memory fact.
- Read and watch tools require `terminal.observe`.
- Write tools require a valid B approval/grant in addition to `terminal.write`.
- Named keys use a new typed A input command; control bytes are not smuggled through the existing plain-text validator.
- Tool errors are structured MCP errors with stable TermFlow error codes.
- Request size, result size, concurrency, and per-binding rate limits are explicit.
- The pinned official SDK supplies transport/parser/handshake primitives only. B explicitly configures and tests the allowed Host/Origin values, agent-token authentication, protocol revision, `Content-Type`/`Accept`, request IDs, session lifecycle, and notification behavior. MCP Streamable HTTP is never exposed to a browser.
- B owns the security checks around the SDK: a dedicated `require_agent_token` that accepts only a hashed AgentToken bound to one binding/Term/runtime epoch, no generic admin/native token fallback, request/result byte limits, timeout, rate/concurrency quotas, and negative tests for missing or mismatched protocol headers. Unknown MCP servers/tools and config drift fail closed.

Every side-effecting tool accepts a B-issued request key. B stores the canonical arguments hash and result under that key; a duplicate key with different arguments is rejected, while a duplicate with the same arguments returns the recorded result. Token issuance reveals a raw token once, stores only its hash, and increments binding epoch on revoke/profile/Term changes.

### 10.1 Protocol compatibility

The implementation pins an OpenCode image and an MCP SDK version together. Contract tests verify the negotiated MCP revision against that exact image. B does not claim compatibility with every historical or draft revision.

## 11. Watch Engine and Durable Continuations

### 11.1 Initial conditions

- `output_contains`: bounded literal match on new output after `start_cursor`.
- `output_idle`: no new output for a duration after at least one observed cursor; wake the agent to inspect, not to assume success.
- `pane_exited`: topology transition.
- `prompt_ready` and `command_finished`: advisory evidence only when shell integration is active. A marker emitted by a pane process cannot grant authority or prove success; an authenticated out-of-band A marker would be required for stronger semantics.

Arbitrary Python regex is excluded from the first release. A later safe-pattern feature requires separate limits and ReDoS analysis.

### 11.2 Evaluation

- `PANE_OUTPUT` is evaluated incrementally as it arrives.
- Silence deadlines use an in-memory deadline heap rebuilt from persistent watches at startup.
- Topology changes evaluate pane exit immediately.
- Watches are edge-triggered from their creation cursor; old scrollback cannot trigger a new watch.
- The cursor contains `instance_id`, a pane incarnation/epoch, `stream_id`, and `seq`. A Term restart or pane replacement invalidates old grants, approvals, and watches for that incarnation.
- B persists the last accepted pane cursor and each active watcher's matcher suffix/cursor transactionally for every consumed live event, not only on trigger. Duplicate, out-of-order, or epoch-rollback events are rejected. Idle timing uses B receipt time rather than A's clock.
- On restart B subscribes before replay, then replays from the persisted cursor when A's bounded ring can prove continuity. A disconnect, gap, or cursor-too-old state marks observation `paused/indeterminate`; `output_idle` cannot fire until topology/stream continuity is re-established and a new verified cursor restarts the timer.
- If A reports a gap or its ring has overwritten the cursor, B performs bounded capture reconciliation with an explicit `snapshot`/`gap_snapshot` kind. Live-only watches do not match snapshot text; the result is an `indeterminate` observation that wakes the agent only to inspect.
- Each trigger creates one durable `WatchDelivery` with an idempotency key.
- The trigger transaction atomically locks the watch generation/cursor, inserts a unique `WatchDelivery`, inserts the causally linked unique `AgentInboxItem`, updates watch state, and commits. The dispatcher only sends committed Inbox items. A duplicate delivery key returns the existing Inbox item and does not wake the backend twice.
- The unique delivery key includes `(watch_id, watch_generation, pane_incarnation, stream_id, trigger_seq/event_id)`. Rearm advances the generation and cursor; a condition that remains true cannot immediately retrigger until a new edge/cursor is observed. Cancellation, expiry, and evaluation race in the same transaction.
- Failed delivery records `attempt_count`, `last_error`, and `next_attempt_at`.
- A Watch targets a product conversation, never only an opaque backend session.

### 11.3 Continuation payload

A Watch stores:

- condition and start cursor
- owning binding and conversation
- human-readable intent summary
- requested wake behavior
- permitted observation scope
- optional proposed next action
- expiry and one-shot/rearm policy, including a persisted `watch_generation` and `rearm_cursor`

When it fires, B creates a typed `WatchTriggered` AgentInput containing the continuation, trigger evidence, and a bounded/redacted latest observation reference or short-TTL excerpt. A proposed action is not pre-approved by being present in continuation text.

## 12. Write Policies and Approval

### 12.1 Policies

**Observe**

- Read panes and manage watches.
- No terminal writes.

**Assisted** — recommended default

- Every write request becomes a persistent `ApprovalRequest`.
- C shows exact text/keys, target Term/Pane, agent identity, reason, and expiry.
- Approval state is `pending -> approved|denied|expired|revoked|consumed|unknown`; a decision is an atomic CAS bound to the approving user session/auth epoch, so stale UI replay and double approval cannot win twice.
- Approval is single-use and bound to a canonical arguments hash covering schema version, operation, instance/pane incarnation, encoded text/key bytes, submit flag, cursor precondition, run/grant ID, expiry, and policy epoch.
- If A or B reports an uncertain execution outcome, the approval is `unknown` and cannot be replayed automatically.

**Delegated (design only; not enabled by default in 0.2.0)**

- A future user-created `WriteGrant` would be bounded by binding/run/pane incarnation, operation allowlist, byte/invocation quota, and time window.
- It must have a random unguessable ID, persistent epoch, atomic single-use consume, and a real A execution receipt before it can be enabled.
- The current direct OpenCode/MCP transport has static binding credentials. Exact conversation-scoped approval therefore relies on B's one-active-run-per-binding invariant; without that invariant the grant must be binding-scoped or the runtime must become per-conversation.
- The UI must state that local tmux input cannot be made a cryptographically exclusive lock unless A gains complete local-input attribution.

There is no unbounded `Autonomous` policy in 0.2.0. Assisted approval is bound to the active binding/run, pane incarnation, exact canonical arguments hash, and a single-use request key; it is not inferred from a backend `always` permission. Typed keys are risk-tiered: navigation keys may be allowlisted, while submit/interrupt/escape/destructive keys require Assisted approval and are never delegated by default.

### 12.2 Final authority

OpenCode permission prompts are useful backend events but do not grant terminal authority. The execution chain is always:

```text
Agent tool call
  -> B scope check
  -> B policy/approval/grant check
  -> B topology and cursor check
  -> CommandRouter audit context
  -> A rechecks pane incarnation and expected cursor under its pane-input lock
  -> A serialized pane input and durable/bounded execution receipt
  -> result or explicit outcome_unknown back to B and Agent
```

Audit includes binding, conversation, run, tool call, approval/grant, pane, command ID, and outcome. Sensitive text is redacted or hashed according to the audit policy rather than copied wholesale. Even this precondition cannot prevent or attribute every local tmux/human input, so neither the API nor UI describes it as an exclusive lock.

The MCP token is never accepted as a generic admin or native-client credential. Agent Chat approval requests use the existing authenticated Web/Tauri user session, an explicit Term ACL, CSRF/Origin protection where applicable, and re-authentication for high-impact actions. OpenCode's `always` permission response is never mapped to B terminal authority; only B's exact single-use approval can authorize a write.

## 13. C Agent Chat and “Agent Speaks Back”

The answer to agent response routing is always B:

```text
OpenCode SSE
  -> OpenCodeAdapter
  -> canonical AgentEvent
  -> persistent B timeline
  -> bounded live fan-out
  -> Web/Tauri Agent Chat
```

C never connects directly to OpenCode.

### 13.1 Client API

- REST creates/lists conversations and pages historical messages/events.
- This is a distinct Agent REST/WS/SSE API and cursor store, not the existing terminal `/api/v1/events` pane stream.
- An authenticated live stream carries new canonical events after an opaque B cursor (global or explicitly conversation-scoped) containing an epoch/reset component. B may assign it from SQLite commit order internally, but storage details are not exposed to C.
- The server subscribes before replaying. If retention/deletion makes a cursor too old, it returns `cursor_too_old` with a snapshot/reset marker instead of silently skipping events.
- Slow clients are disconnected from live fan-out and recover from REST replay.
- Agent streams track binding/conversation identity and subscribe to revocation events; binding revocation or auth epoch change closes them even though the existing terminal EventHub only carries instance/auth-epoch metadata.

### 13.2 Web and Tauri

- Shared `client-core` defines the Agent Conversation and stream ports.
- Web adapter uses the approved browser Cookie/Origin path.
- Tauri adapter uses Rust-owned HTTP/WS transport and keeps credentials out of the WebView.
- Shared Vue Agent Chat depends only on the runtime port.
- Approval UI reuses the existing accessible dialog, focus, error retention, and Toast patterns.
- Agent text, tool reasons, terminal excerpts, and approval context render as plain text or a strict Markdown allowlist. Raw HTML, scripts, ANSI/OSC, `javascript:` URLs, and executable links are rejected.

## 14. Voice and STT

Voice is an input adapter, not part of the Agent Backend contract:

```text
C records bounded audio
  -> B TranscriptionProvider
  -> transcript draft
  -> C user confirms/edits
  -> normal UserMessage AgentInput
```

Requirements:

- Text chat remains fully functional when STT is absent.
- B defines a `TranscriptionProvider` port.
- An optional separately deployed STT container may implement it.
- Audio `Content-Length`, decoded frame count/duration, sample rate, magic MIME type, concurrency, and timeout are bounded before and after decoding; temporary files, proxy buffers, provider failures, and all error paths are cleaned up.
- B stores a short-lived `TranscriptDraft` (`draft -> confirmed|cancelled|expired|consumed`) with owner/binding/**target conversation**, provider/region, expiry, transcript hash, and disclosure/retention metadata. Raw audio is deleted after transcription by default and is not logged.
- Only the same authenticated user may explicitly confirm/edit a non-expired draft once. A `UserMessage` references that draft ID and target conversation in one-time CAS; agents, backend callbacks, and generic APIs cannot submit an unconfirmed draft or replay it into another conversation.
- Transcript is shown for confirmation before it can cause an Agent turn.
- Browser `SpeechRecognition` may be an optional convenience adapter, not the portable core path.
- STT provider, locality, external disclosure, and model download requirements are visible in deployment settings.

## 16. Docker and Security Boundary

Reference deployment:

```text
public/LAN network: A/C <-> B Control Plane
agent_internal (internal:true): B <-> termflow-agent-opencode
provider_egress (optional, allowlisted): OpenCode -> model provider only
```

OpenCode container rules:

- Pin an exact tested version and image digest; never use `latest`.
- Verify image signature/provenance/SBOM and a release-time CVE gate; use a version containing all published security fixes.
- Do not publish port `4096` to the host in the default deployment.
- OpenCode is not attached to the public A/C network. Its egress network has a DNS/TLS destination allowlist and cannot reach B's generic admin/instance routes; MCP uses a dedicated listener/route with AgentToken auth. Document the bridge-only HTTP threat model or use mTLS/a local connector where that is insufficient.
- Use HTTP Basic auth on the internal B-to-OpenCode connection and rotate the secret.
- Pass model credentials through deployment secrets, not image layers or committed env files.
- Start OpenCode from a pinned, non-user-overridable config with permission `"*": "deny"`; allow only exact reviewed TermFlow MCP tool names. Disable unknown built-ins, extra MCP servers, user config injection, and `always` permission escalation.
- Do not mount the Docker socket, A directories, TermFlow credentials, or arbitrary host workspaces.
- Run as a non-root fixed UID with `cap_drop: [ALL]`, `no-new-privileges`, a read-only root filesystem plus bounded `tmpfs`, default/custom seccomp and AppArmor, and CPU/memory/PID/ulimit constraints. No host network, privileged mode, or extra network attachment is allowed.
- Use a dedicated data volume only if backend conversation persistence is enabled.
- Bound and redact Docker/OpenCode HTTP/JSON logs; never log credentials, raw SSE, terminal/tool content, or provider payloads.
- Product deletion must remove the corresponding backend session and retained volume data according to policy; if cleanup is unavailable it remains `deletion_pending` and is retried/alerted.
- Add healthcheck, dependency readiness, shutdown, and reconciliation tests.

Terminal excerpts sent to OpenCode may be forwarded to an external model provider. The UI and deployment documentation must disclose this before enabling the Agent Binding.

### 16.1 Data retention defaults

The release ships explicit, configurable ceilings rather than an unspecified “bounded” promise:

| Data class | Default retention / limit |
|---|---|
| Final product messages and durable timeline | 30 days; owner/Term ACL; user delete available |
| Streaming assembly checkpoints | 24 hours and per-run byte quota |
| Terminal/watch excerpts | 24 hours, redacted, at most 64 KiB per event; raw pane stream is not persisted |
| User-approved memory facts | 90 days unless the user chooses a shorter expiry; per-scope count/byte quota |
| Approval/audit metadata | 90 days; text stored as hash/redacted metadata where possible |
| Unknown/debug diagnostics | 24 hours; metadata only unless audited debug opt-in |
| Transcript draft / raw audio | 1 hour / deleted immediately after transcription or failure |
| OpenCode volume / container logs | conversation policy / 7 days with size rotation and redaction |
| Confirmed cleanup tombstone | 30 days; no copied content |

Backups, SQLite WAL, Docker logs/volumes, and external-provider retention are part of the same policy. SQLite row deletion is logical rather than guaranteed physical erasure; sensitive short-lived blobs use per-record encryption/crypto-erasure where implemented, otherwise the UI states the backup/WAL retention window. Enabling an external provider records endpoint, model, region, retention/no-training terms, and user consent; unknown or drifted policy disables the binding.

## 17. Failure and Recovery Semantics

| Failure | Required behavior |
|---|---|
| A disconnects | Reads report offline; watches remain pending and inactivity deadlines pause; writes fail closed. Reconnect requires topology/incarnation plus stream replay/snapshot reconciliation before a deadline restarts. |
| Pane stream gap | `pane_read since` returns explicit gap; agent must request bounded snapshot. |
| OpenCode unavailable | Inbox remains durable with retry/backoff; C sees backend unavailable. |
| SSE disconnect | Adapter reconnects and reconciles; uncertain action turns are not blindly resubmitted. |
| B restarts | Recover in order: DB integrity/migration; increment runtime epoch and fence stale runs/claims; reconnect and reconcile A topology/streams; reconnect OpenCode/SSE and reconcile nonterminal sessions/runs; rebuild watch cursors/deadlines; only then dispatch pending Inbox. |
| C disconnects | Agent continues; C replays B timeline using its cursor. |
| Approval expires | Write fails; a new exact approval is required. |
| Binding/token revoked | MCP and Agent streams fail closed; active grants are invalidated. |
| Term deleted | Agent conversations/watches are cancelled; a durable tombstone/cleanup job retries backend, volume, log, memory export, and provider cleanup. Failure remains visible as `deletion_pending`/dead-letter. |
| STT timeout | Audio is deleted; transcript is not submitted; text input remains available. |

Crash-safety claims must name the SQLite durability level (`synchronous=FULL` or the documented power-loss window), busy/transaction locking, WAL checkpoint/backup policy, and `integrity_check` recovery. Process restart tests alone do not prove power-loss durability.

## 20. Required Test Matrix

### Domain and persistence

- Plugin registry ordering, duplicate registration, disabled Agent Broker startup, plugin migration ownership, and plugin shutdown/restart behavior.
- Disabled-plugin capability discovery hides Agent UI and closes Agent streams while existing Term/terminal routes continue to work; already-applied Agent schema remains compatible with central migration head.
- State transitions, claiming, retry, cancellation, expiry, deletion, and restart.
- Multiple conversations per Term and shared memory isolation.
- Backend ID opacity and no Term/binding/conversation ID substitution.
- Cross-Term repeated pane IDs.
- Fault injection before/after Inbox claim commit, socket write, OpenCode `204`, SSE normalization/event commit, Watch cursor/delivery/Inbox transaction, approval consume, A enqueue/send/receipt, cleanup tombstone, and live fan-out.
- `kill -9`/WAL commit-rollback, busy-writer, checkpoint, backup/restore, `integrity_check`, and the documented power-loss durability level.

### Terminal observation and watches

- Cursor ordering, duplicate chunks, gaps, reconnect, bounded captures, very large history, Unicode, and split control sequences.
- Watch creation after matching text, edge-only trigger, silence reset, pane exit, expiry, rearm, and outbox crash points.
- A restart/ring overwrite/backpressure, snapshot never matching live output, topology change while B is offline, cursor epoch rollback/spoofed instance envelope, and a literal match split across chunks.

### Permissions

- Observe rejects every write.
- Assisted requires exact unexpired approval.
- Changed text, pane, run, cursor, or expiry rejects reuse.
- Revocation and restart invalidate active authority as designed.
- OpenCode permission approval never bypasses B policy.
- Concurrent/double/replayed approvals, stale auth epoch, canonical-hash mutation, risky key classes, local-input race disclosure, and unknown A write outcome.

### Backend

- Fake backend contract tests for domain behavior.
- Pinned real OpenCode contract tests for endpoints and event mapping.
- SSE disconnect/reconcile and action delivery uncertainty.
- Scoped backend event subscriptions reject mismatched binding/runtime epochs and duplicate provider session IDs; stale or unknown notifications are dropped and counted.
- Reasoning/attachment/unknown-part suppression, `messageID` duplicate fixture, cancel race, backend context loss with/without persistent volume, and stale runtime-epoch tool calls after B restart.
- Real OpenCode tool inventory proves `"*": "deny"`, exact TermFlow MCP allowlist, no extra MCP/plugin/LSP/downloaded tool, `always` cannot bypass B, and config drift fails startup.
- MCP Host/Origin/token/scope/epoch/content negotiation, side-effect request-key replay, two-binding isolation, and same-binding serialized attribution.

### Clients and privacy

- Web/Tauri authentication, replay, slow consumer, focus/accessibility, and approval failure retention.
- No raw token, provider credential, unbounded terminal content, or raw audio in logs/database.
- Conversation/Term deletion removes B records and requests backend cleanup.
- External provider disclosure and enablement confirmation.
- Agent/terminal output HTML, ANSI/OSC, dangerous URL, secret-canary, absolute-path, and prompt-injection rendering/persistence tests.

- Deletion while backend/provider is unavailable proves `deletion_pending`, retry/dead-letter, WAL/backup/log/volume cleanup, and audited completion.

## 21. Discussion Gates

The plan uses these recommended defaults until the user changes them:

1. **Backend switching:** switch or fork at a new Agent Conversation; do not promise lossless mid-conversation migration.
2. **Default authority:** Assisted; Observe is available. Delegated remains a disabled future capability in the shipped 0.2.0 profile, and unlimited Autonomous is excluded.
3. **Memory:** one curated B-owned memory scope per `(Term, Agent Profile)`; backend session context is not portable memory.
4. **Voice:** included as a late, optional deployment slice; text Agent features do not depend on STT.
5. **Watches:** literal output, inactivity, and pane exit are baseline; trusted command markers are an optional capability.
6. **Deployment/isolation:** one separately deployed OpenCode runtime per Agent Binding by default, controlled through the required `AgentRuntimeSupervisor` contract; same-binding conversations are serialized, and changing the active conversation rotates the epoch-bound MCP capability and supervisor-quiesces/restarts the runtime. Avoiding that restart requires a trusted connector with proven per-conversation tool-call identity. The Compose example demonstrates one binding; B remains single-worker and SQLite-backed.
7. **Terminal content:** only bounded excerpts are sent to the agent; raw streams are not durably stored by default.
8. **B plugin boundary:** `agent_broker` is a trusted first-party Feature Plugin with explicit enable/disable configuration. It is not an arbitrary runtime-installed Python plugin; third-party extensions require a future sandboxed out-of-process protocol.
9. **Parallel execution:** after M0, P1–P6 may proceed independently against frozen contracts and fake dependencies; shared schema/composition/deploy files use an integration owner and serial merge gates.

Review these gates before expanding each milestone into code-level, 2–5 minute TDD tasks.

## 22. Reuse Audit and Adoption Decisions

The rule for reuse is: adopt a library when it removes a protocol/parser/transport burden without taking ownership of TermFlow's authority, persistence, or recovery semantics. Use an adapter/projection when an external protocol is useful but its IDs, retention, or security model do not match B. Do not add infrastructure merely because it already implements a similar-sounding feature.

| Candidate | Reuse boundary | Decision for 0.2.0 |
|---|---|---|
| Official MCP Python SDK v2 | B's MCP server/client transport, protocol negotiation, tool schemas, Streamable HTTP | **Adopt directly.** Do not hand-write JSON-RPC/MCP framing. Keep B's AgentToken, Origin/Host, scope/epoch, limits, and policy checks outside the SDK. [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk) |
| OpenCode Server/SDK contract | First `AgentBackend` implementation and HTTP/SSE decoder | **Adopt directly.** Pin `/doc`, generated types, image digest, event mode, and compatibility fixtures. Do not expose OpenCode types in the domain. [OpenCode Server](https://dev.opencode.ai/docs/server/) |
| Pluggy | In-process hook dispatch for the trusted B Feature Plugin registry | **Likely adopt, narrowly.** Use hookspecs/registration to avoid inventing a plugin call dispatcher, but wrap it with typed `BFeatureContext`, route/event/migration registries, dependency ordering, and import-lint rules. Pluggy is not a sandbox, ACL layer, lifecycle manager, or migration runner. [Pluggy](https://pluggy.readthedocs.io/en/stable/) |
| AG-UI | C-facing projection of run/message/tool/state events | **Evaluate/adopt as a wire projection.** Its event, snapshot/delta, interrupt, and SSE/WebSocket-friendly model can reduce client protocol work. B keeps its own durable canonical event/cursor/auth model; AG-UI IDs and events are not the database contract. [AG-UI](https://docs.ag-ui.com/) |
| `sse-starlette` | Optional B Agent SSE response implementation | **Direct optional reuse.** Use it if the Agent stream exposes SSE; keep subscribe-before-replay, opaque cursors, auth epoch closure, backpressure, and retention logic in B. [sse-starlette](https://github.com/sysid/sse-starlette) |
| `pyte` | Stateful VT/ANSI terminal rendering for Observation Service | **Evaluate behind `TerminalObservationPort`.** It can replace a custom screen-state parser, but does not provide tmux stream cursors/gap/incarnation semantics. Its LGPL-3.0 license and escape-sequence behavior require a compatibility/security fixture before adoption. [pyte](https://github.com/selectel/pyte) |
| `libtmux` | Non-streaming tmux object traversal, provisioning, and isolated test fixtures | **Partial reuse only.** It provides typed Server/Session/Window/Pane operations, send/capture helpers, and pytest fixtures, but it does not replace the existing BridgeRuntime control-mode stream, bounded ring, or A/B protocol. [libtmux](https://github.com/tmux-python/libtmux) |
| OpenAI Whisper / faster-whisper | Optional STT container implementation behind `TranscriptionProvider` | **Adopt as a provider plugin, not B logic.** `faster-whisper` is a CTranslate2 implementation suitable for a pinned CPU/GPU container; B still owns upload limits, raw-audio deletion, draft confirmation, provider disclosure, and no-auto-submit. [Whisper](https://github.com/openai/whisper), [faster-whisper](https://github.com/SYSTRAN/faster-whisper) |
| Temporal / Restate | Durable workflows, timers, signals, retries, and crash recovery | **Future 0.3+ option, not 0.2 default.** Both could replace much of the custom Watch/Inbox scheduler, but require a workflow service/worker deployment and change the current SQLite single-worker model. [Temporal](https://docs.temporal.io/), [Restate](https://docs.restate.dev/develop/python/services) |
| NATS JetStream / Redis Streams | Durable event transport, replay, consumer groups, and multi-worker delivery | **Future scale-out option.** JetStream offers durable streams/consumers and replay; Redis Streams offers ordered streams, consumer groups, ack/reclaim, and configurable retention. Neither should replace B's canonical authorization/timeline transaction in 0.2. [NATS JetStream](https://docs.nats.io/nats-concepts/jetstream), [Redis Streams](https://redis.io/docs/latest/develop/use-cases/streaming/) |
| A2A / ACP | Future remote-agent or agent-client interoperability | **Do not use as the 0.2 OpenCode transport.** A2A is a future agent-to-agent adapter boundary; ACP is a separate client/agent protocol and OpenCode's current integration is stdio/bridge-shaped. Add only after a transport and capability fixture exists. [A2A](https://github.com/a2aproject/A2A), [ACP](https://agentclientprotocol.com/protocol/v1/overview) |

### 22.1 Reuse invariants

- A reused protocol/library may parse, transport, schedule, or render data; it does not become the authority for Term ACL, AgentToken, approval, pane incarnation, B cursor, deletion, or retention.
- Every reused component is hidden behind a TermFlow port: `BFeatureContext`, `AgentBackend`, `BackendToolConnector`, `TerminalObservationPort`, `TerminalCommandPort`, `ContinuationPort`, or `TranscriptionProvider`.
- Provider-only types, MCP parts, AG-UI events, tmux wrapper objects, and STT model objects do not enter `packages/protocol` or the canonical B/C domain models.
- Direct adoption requires pinned version/license/SBOM checks, a contract fixture, bounded payload tests, and a failure/reconnect test. “Popular” is not itself a compatibility or security argument.

### 22.2 Recommended implementation order

1. Use the official MCP SDK and OpenCode generated contract immediately.
2. Use Pluggy only for first-party in-process hook dispatch, with TermFlow typed registries around it.
3. Reuse `libtmux` selectively for test/provisioning helpers; keep the existing A control-mode stream.
4. Evaluate `pyte` before writing another stateful terminal renderer; reject it if license or parser fixtures fail.
5. Project B events to AG-UI only after the durable B timeline/cursor contract is stable.
6. Add faster-whisper as the first optional STT provider plugin.
7. Defer Temporal/Restate and NATS/Redis until SQLite/single-worker limits are actually reached.
