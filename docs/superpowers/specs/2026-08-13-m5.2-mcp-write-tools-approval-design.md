# M5.2：MCP 写工具接线与审批流设计

## 背景

1. 把 MCP 写工具（`termflow_pane_send_text` / `termflow_pane_send_keys`）接到 B 的

## 目标

让 OpenCode（或其他 MCP 客户端）提议 pane 写入，且**只有在 B 授权后**才执行：

- `termflow_pane_send_text` / `termflow_pane_send_keys` 注册到 MCP server，执行
  B 侧的 scope 检查、pane 策略检查、会话归属检查，然后进入持久化单次审批流。
- 写工具调用同步等待人工审批（MCP 工具是同步 request/response），审批通过后经由
  `CommandRouter`/A 输入路径执行，并返回结构化回执（confirmed / failed /
  outcome_unknown）。
- 不确定的 A 执行结果消耗审批权限（`unknown`），绝不自动重发。
- 审批创建、决策、执行结果与撤销全部写入审计，包含 agent 身份与审批上下文；
  文本/按键原文不落库（只落 canonical hash 与有界元数据）。
- Delegated Write Grants 保持禁用：0.2.0 无任何代码路径读取 `write_grants`，
  能力标志恒为 False。

  `"admin"`（沿用 M5.1 的已记录限制；精确身份属后续里程碑）。

## 设计

### 1. 写工具调用时序（同步等待审批）

```
MCP tool call (send_text / send_keys)
  -> _require_write_scope (terminal.write)            [fail closed]
  -> pane allowlist 检查 (pane_observe_allowed)       [fail closed]
  -> conversation 归属检查 (conversation.binding_id)  [fail closed]
  -> CommandService.execute(principal, tool_call_id, params)
      1. 收集 B 侧上下文并计算 canonical_hash
      2. policy.create_approval(...)  持久化 pending 审批（单次、含 hash）
      3. 轮询等待人工决策（DB 轮询，间隔 0.5s）
         - approved -> 执行前重检 -> 发送 -> 按结果 settle
         - denied   -> 结构化 MCP 错误 approval_denied
         - revoked / expired -> 结构化 MCP 错误 approval_revoked / approval_expired
         - 等待超时 (approval_wait_timeout_seconds) -> 撤销 pending
           (actor="system:tool_timeout") -> MCP 错误 approval_required + approval_id
      4. 任何非执行退出路径的 finally：若审批仍为 pending 则尽力撤销
```

决策点：**同步等待**而不是"立即返回 + 客户端轮询"。理由：MCP 工具调用是同步
request/response；"立即返回"会让已批准的写没有执行者（agent 重试会产生第二个审批
与重复的 UX），而同步等待把"创建-决策-执行-回执"绑定为一个可追踪的调用。等待受
`approval_wait_timeout_seconds`（默认 25s）约束，并必须小于 guard 的
`tool_timeout_seconds`（默认 30s）——`McpGuardrailConfig.__post_init__` 强制校验。

等待期间占用 binding 的并发额度槽（默认 2/binding）：可接受的限制，写入请求本
身低频，且文档明确。

**超时语义**：等待超时即撤销 pending 审批（一个已撤销的审批不可能在事后被批准为
"已通过但无人执行"的僵尸状态；事后决策得到 409 `approval_revoked`，UI 语义清晰）。
OpenCode 若仍想写入，会以新的 tool_call_id 重发工具调用 → 新的审批 → 人工再次
决策。这不是自动重发：B 从不主动重发，每次执行都有人工决策。

### 2. 执行路径：CommandService → CommandRouter → A

新增 `CommandService`（实现 `TerminalCommandPort`，替换 `UnsupportedCommandService`），
依赖注入：

- `repositories: RepositoryBundle`、`sessions: async_sessionmaker`（构造
  `ApprovalPolicy`）
- `gateway: CommandGateway`（新协议，见下）
- `observation: TerminalObservationPort`（用 `resolve_cursor` 取 pane
  incarnation/cursor 账本）
- `clock`、审批等待/TTL 配置

`CommandGateway` 协议（agent_broker 内部，可测缝）：

```python
class CommandGateway(Protocol):
    async def send_text(self, instance_id, pane_id, text, submit,
                        idempotency_key, pane_incarnation) -> CommandResultPayload
    async def send_keys(self, instance_id, pane_id, keys,
                        idempotency_key, pane_incarnation) -> CommandResultPayload
```

生产适配器 `CommandRouterGateway` 包装 `CommandRouter` 并映射错误：

- `CommandRouter.send_input` 增加可选参数 `pane_incarnation: int | None = None`
  （缺省 None，C 终端输入路径行为不变）；agent 写路径总是传入账本值。
- 新增 `CommandRouter.send_keys`：镜像 `send_input`（拓扑检查、入队新
  `PANE_KEY_INPUT` 消息、按 command_id 关联回执、`pane.keys` audit），并在入队前
  `connection.require_capability(typed_keys=True)` fail closed。
- `TermFlowError` 映射：`command_timeout` / `outcome_unknown` → 抛出
  `OutcomeUnknownError`（`TermFlowToolError`，code `OUTCOME_UNKNOWN`），表示
  **不能证明结果**；其余已知失败逐一映射：`instance_offline` →
  `INTERNAL_ERROR`、`topology_unavailable` → `INTERNAL_ERROR`、
  `pane_not_found` → `PANE_NOT_FOUND`、`backpressure` → `INTERNAL_ERROR`
  （与观察路径的 backpressure 语义一致）。
  `CapabilityUnavailable` → `POLICY_DENIED`。
- A 侧回执 `error_code` 映射为稳定 `TermFlowErrorCode`（`pane_not_found` →
  `PANE_NOT_FOUND`、`invalid_key` → `INVALID_REQUEST`，其余 → `INTERNAL_ERROR`，
  与 `terminal_ports.py` 的 `_WIRE_ERROR_CODES` 模式一致）。

**typed keys 线上消息**（计划 §10 第 553 行的要求）：在
`packages/protocol` 新增：

- `PaneKeyInputPayload`（`command_id`、`idempotency_key`、`pane_id`、
  `keys: tuple[str, ...]`，长度 1..`MAX_KEY_SEQUENCE_LENGTH`），校验通过共享的
  命名键词表。
- `MessageType.PANE_KEY_INPUT`。
- 两个输入消息（`PaneInputPayload`、`PaneKeyInputPayload`）增加可选字段
  `pane_incarnation: int | None`：agent 写路径总是填充（来自 B 账本）；C 终端输入
  路径不传（保持现有行为不变）。A 在消息存在时校验（与 capture 请求的
  incarnation 校验同模式，runtime.py 265 行）；缺省时跳过 incarnation 校验、
  保留现有 pane 存在性校验。
- `termflow_protocol/keys.py`：钉死命名键词表 `NAMED_KEYS`（有界集合，约 55 个：
  `space`/`tab`/`enter`/`backspace`/`escape`/`delete`/`insert`/`home`/`end`/
  `pageup`/`pagedown`/`up`/`down`/`left`/`right`/`f1..f12`/`ctrl-a..z`/
  `alt-a..z`/`shift-tab`；小写精确匹配）+ 规范编码
  `canonical_key_bytes(keys) -> bytes`（位置敏感的 JSON 数组，无 sort_keys）。
  词表不在集合内的名字 → `INVALID_REQUEST`（B 侧早拒）与 A 侧 fail-closed。
  plain 字符（如 `"a"`）不是命名键，agent 应使用 `send_text`。

A 侧改动：

- `BridgeHello.typed_keys` 改为 True（transport.py 245 行；旧 A 缺省 False →
  B 的 `require_capability` 拒绝，fail closed）。
- `InputHandler` 增加 `handle_keys()`：与文本共用 `_pane_locks` 与
  `IdempotencyResults`（同一 pane 的文本/按键写入互斥）；校验词表后调用
  `TmuxRunner.send_keys(pane_id, keys)`（`tmux send-keys -t <pane> <tmux名...>`，
  单次调用传多个名字）。协议名字 → tmux 键名的映射表钉在 node 侧
  （`termflow_node/bridge/key_names.py`），fixture 测试断言映射覆盖
  `NAMED_KEYS` 全集；未知名字 → `CommandResultPayload(ok=False,
  error_code="invalid_key")`。
- `runtime.py` 分发 `PANE_KEY_INPUT`，回执复用 `COMMAND_RESULT`。
- `command_id` 关联复用 B 侧 `connection.pending`（bridge.py 117-121 行已按
  command_id 弹回执，无需改动）。

`idempotency_key`：每次执行 `uuid4()`。审批 consume 是真正的重放闸（发生在发送
之前由 tool_call_id 唯一性保证），B 从不自动重发，因此不需要确定性 key。
`request_key`（协议字段，客户端簿记）不参与 canonical hash：写入由
pane/text/keys/submit 定义，`request_key` 只是回执回显；保持 M5.1 的
`FIXED_HASH_VECTOR` 不变。

### 3. canonical_hash 输入（M5.2 填充）

`ApprovalArgsHashInput` 保持不变（M5.1 已锁定 schema v1 编码与测试向量），
CommandService 按写工具语义填充：

| 字段 | send_text | send_keys |
|---|---|---|
| `schema_version` | 1 | 1 |
| `operation` | `"send_text"` | `"send_keys"` |
| `instance_id` | `principal.instance_id` | 同左 |
| `pane_id` | `params.pane_id` | 同左 |
| `pane_incarnation` | 账本当前值 `str(int)`；未知则 `"1"`（与读路径缺省一致） | 同左 |
| `encoded_bytes` | `text.encode("utf-8")` | `canonical_key_bytes(keys)` |
| `submit` | `params.submit` | `False`（enter 是键名） |
| `cursor_precondition` | 账本 `"{stream_id}:{seq}"`；无账本则 `None` | 同左 |
| `run_id` | 会话当前 running run（`agent_runs.list_for_conversation` 中
  `run_state == "running"`）；无则 `None` | 同左 |
| `grant_id` | 恒 `None`（Delegated 禁用） | 同左 |
| `expiry` | `now + approval_ttl_seconds`（默认 300s，aware UTC） | 同左 |
| `policy_epoch` | 当前持久化 auth epoch（`persisted_authentication_epoch`） | 同左 |

`policy_epoch` 的取值为持久化 auth epoch：B 目前唯一带 epoch 语义的状态；把 auth
epoch 绑进 hash 与 `decide` 的 CAS 一致，auth 重置后一切旧审批失效（fail closed）。
将来引入独立策略版本时以 `schema_version` 递增并新增字段，必须同步更新测试向量。

### 4. 执行前重检与 settle（single-use 语义）

等待循环看到 `approved` 后，执行前按序重检：

1. `approval.auth_epoch == 当前持久化 auth epoch`，否则
   `revoke(actor="system:auth_epoch_changed")` + 拒绝（`POLICY_DENIED`）。
2. `now < approval.expires_at`，否则拒绝（状态由 sweep 收尾）。
3. binding 仍为 `pending`/`ready`。
4. **用当前账本值重算 canonical_hash**：任何字段（文本/按键、pane、incarnation、
   cursor、run、expiry、epoch）与存储 hash 不符 → 目标已漂移 →
   `revoke(actor="system:target_changed")` + 结构化错误
   `INCARNATION_CHANGED`（消息说明 cursor 或 incarnation 差异；agent 应重新
   `pane_read` 后重试）。这覆盖"并发人工输入/输出推进 cursor"与"pane 被替换"。
5. 发送前做**最后一次状态读取**（必须仍为 `approved`，否则不发送并退出）；
   随后立即发送（文本或按键），然后 settle。该最终读取与入队之间的 revoke 竞态
   属于"在途写入"：发送照常完成并照实返回，状态为 revoked，审计记录（见下文
   撤销竞态披露）。

| A 结果 | settle 状态 | MCP 回执 |
|---|---|---|
| `result.ok`（tmux send 确认） | `consume` | `ok=True, outcome="confirmed"` |
| 已知失败（`pane_not_found`/offline 于发送前/backpressure 等） | `consume` | `ok=False, outcome="failed", error_code=<映射>` |
| 不确定（发送后等待回执时 `command_timeout`/连接断开） | `mark_unknown` | `ok=False, outcome="outcome_unknown", error_code="outcome_unknown"` |

settle 的 CAS 就是单次使用闸：只有一个 settle 能赢；settle 竞争失败（例如执行间隙
被人工 revoke）时不再改状态，但仍返回事实回执（写入确实发生了，审计照记）。
`mark_unknown` 保持 M5.1 的 `approved → unknown` 语义（终态、不可重放），
`consume` 保持 `pending|approved → consumed`。**不做** `consumed → unknown`：
发送先于 settle，因此执行间隙只有 revoke 竞争，不存在"已 consume 再发现 unknown"
的路径。

**撤销竞态披露**：`revoke` 在发送开始前生效；已入队/在途的写入无法召回（与本地
tmux 输入同理）。审计记录该结果；文档与 API 错误说明这一限制。

### 5. 状态清扫与 B 重启恢复

- 等待超时撤销（见 §1）：pending → revoked（actor `system:tool_timeout`）。
- `expire_pending` 扩展为过期清扫 `pending` **和** `approved`（approved 且过期
  只能来自"决策后未执行"的僵尸，0.2.0 中唯一消费者是同步工具调用）：两者 →
  `expired`。执行路径自身的 expires_at 重检保证一致性（sweep 与执行互不矛盾）。
- **B 重启**：所有在途工具调用死亡，因此：
  - `pending` → `revoked`（actor `system:restart`）——从未决策、无等待者；
  - `approved`（未 consume）→ `unknown`（actor `system:restart`）——不能证明
    是否已执行，绝不自动重放。
  挂在 `run_agent_recovery`（plugin.py 71 行）之后作为同一启动顺序的一部分，
  计数并入 recovery 报告。
- binding 状态改为 `revoked`/`disabled`（`agent_admin.update_binding`）时调用
  `policy.revoke_for_binding(binding_id)`；binding 删除由 FK CASCADE 处理。
  auth epoch 变化**不做**批量撤销：`decide` CAS（M5.1）拒绝陈旧决策，执行前重检
  ①拒绝陈旧批准，已足够。

### 6. MCP server 接线与 scope 门槛

- `_register_observe_tools` 扩展为注册全部 8 个工具（保留自检：注册集合必须等于
  声明集合，否则 `ToolConfigDriftError`；`OBSERVE_TOOLS` 常量更名为 8 工具
  全集）。`DEFERRED_WRITE_TOOLS` 变为空集合，
  `check_tool_config_drift` 因此要求 `registered == pinned allowlist` 精确相等；
  固定 OpenCode 配置 fixture 已 allowlist 全部 8 个工具，无需改 fixture。
- HTTP 认证门槛 `required_scopes=[SCOPE_TERMINAL_OBSERVE]` 不变（最低门槛）；
  写工具在 handler 内执行 `_require_write_scope`（`SCOPE_TERMINAL_WRITE` 缺失 →
  `POLICY_DENIED`），与观察工具的 `_require_observe_scope` 同模式。**双门槛
  fail-closed**：token 只有 observe scope 时写工具在 handler 拒绝；token 有 write
  scope 但无 observe scope 时读取仍拒绝。
- `_guarded_tool`/`_run_guarded`：写工具通过 `ctx.request_id` 注入
  `tool_call_id`（无 ctx/request_id → `INVALID_REQUEST`）；`_ToolPorts` 增加
  `commands` 端口，`kwargs_for` 对写工具返回
  `{"commands": ..., "repositories": ...}`。
- `build_mcp_server` 增加 `sessions`（构造 `ApprovalPolicy`）与 `commands`
  参数；`McpGuardrailConfig` 增加 `approval_wait_timeout_seconds`（默认 25.0，
  校验 < `tool_timeout_seconds`）与 `approval_ttl_seconds`（默认 300.0）。
- 写工具 handler 的对话归属检查与 `watch_create` 相同
  （`conversation.binding_id == principal.binding_id`）；pane 写入同样要求 pane
  allowlist（复用 `pane_observe_allowed`；不能观察的 pane 绝不能写）。
- **backend `always` 无法绕过**：写 handler 不接受任何权限声明参数（协议模型
  `extra="forbid"`），每次调用无条件创建审批；B 侧不存在"已授权快路径"。
- 重放语义：`create_approval` 的 `(conversation_id, tool_call_id)` 唯一约束拒绝
  同一工具调用的任何重放（不同参数 → `approval_conflict`；相同参数 → 同样
  `approval_conflict`，data 中带该审批的终态）。`TermFlowErrorCode` 增加
  `APPROVAL_EXPIRED`、`APPROVAL_REVOKED`、`APPROVAL_CONFLICT` 三个值（与 REST
  词汇一致）。

### 7. 审计（agent 身份 + 审批上下文）

新增表 `approval_audit_events`（模型 `ApprovalAuditEvent`，迁移 0008），
列（全部为元数据，无文本/按键原文）：

`id`、`created_at`、`event_type`（`created`/`decided`/`revoked`/`consumed`/
`unknown`/`expired`）、`approval_id`（FK CASCADE）、`binding_id`、`instance_id`、
`runtime_epoch`、`conversation_id`、`run_id`（可空）、`tool_call_id`、`pane_id`
（可空）、`operation`（可空）、`input_bytes`（可空，字节数而非内容）、
`canonical_hash`、`auth_epoch`、`actor`（可空：`"admin"` 或
`system:tool_timeout`/`system:restart`/`system:auth_epoch_changed`/
`system:target_changed`）、`outcome`（可空，写结果：`confirmed`/`failed`/
`outcome_unknown`）、`error_code`（可空）。

写入点：`ApprovalPolicy` 注入可选的 `ApprovalAuditWriter`（缺省 no-op，保持 M5.1
测试不变；组合根构造真实实现并置于 `app.state`，`api/agent_approvals.py` 与

接受可选的 `outcome`/`error_code` 元数据参数（只进审计，不改 CAS 语义）。

writer 与 sessions）：仓库方法返回被清扫行的 ID，policy 逐行记录 `expired`
审计事件（有界，行数小）。

- agent 身份 = binding_id + instance_id(term) + runtime_epoch + run_id；
- 审批上下文 = approval_id + tool_call_id + canonical_hash + auth_epoch +
  pane/operation/input_bytes；
- 原文不落库：`raw_storage=False`、`redacted=True`，与
  `APPROVAL_AUDIT_METADATA`（90 天）契约一致。
- `RepositoryBundle.purge_expired` 增加 90 天过期删除。
- 人类决策者身份沿用 `"admin"`（M5.1 限制，文档记录；精确身份捕获在后续里程碑）。

## 安全

- scope 双门槛：HTTP 门槛 `terminal.observe` + handler 门槛 `terminal.write`；
  两者独立 fail closed。
- pane 策略：写工具复用 pane allowlist；未 allowlist 的 pane 拒绝。
- 归属：conversation 必须属于 principal 的 binding；`instance_id` 恒来自
  principal（不接受调用方传入的 term_id）。
- 重放：`(conversation, tool_call_id)` 唯一 + settle CAS + 执行前 hash 重算；
  任何参数/状态变化都拒绝复用。
- 权限消耗：确认与已知失败 → `consumed`；不确定 → `unknown`；`unknown` 与
  `consumed` 均为终态，永不自动重发。
- 原文不落库：文本/按键只进 canonical hash 与内存（等待窗口），审计与审批行只存
  元数据；`input_bytes` 只记字节数。
- 命名键词表钉死：B 早拒未知键名；A 二次校验并只把映射后的 tmux 键名传给
  `send-keys`（绝不透传任意字符串）；映射 fixture 防漂移。
- typed_keys 能力未协商（旧 A）→ `require_capability` 拒绝按键写入。
- backend `always` 权限响应与 B 审批无关：写 handler 无权限声明输入面；
  `_permission_response_body` 已拒绝 `always`（既有测试保持）。
- 并发：binding 额度（2）限制同时在途审批；等待中的审批占一个并发槽（文档化）。

## 风险与缓解

1. **同步等待 vs OpenCode 客户端工具超时**：若 OpenCode 在 B 返回前自行超时，
   工具调用可能已取消而审批已创建。缓解：等待窗口（25s）远小于 B 侧 guard
   （30s）；超时即撤销（无僵尸审批）；agent 重试是新 tool_call_id → 新审批 →
   人工再次决策（非自动重发）；错误携带 approval_id 便于关联。
2. **严格 cursor 前置条件导致正常写入被拒**（等待窗口内任何 pane 输出都推进
   账本）：缓解：等待窗口短；拒绝码稳定（`INCARNATION_CHANGED` + 消息说明）；
   agent 的"重新 read → 重新请求"是设计好的恢复回路；错误文本明确
   `system:target_changed` 语义。此严格性是计划的 fail-closed 意图（矩阵要求
   cursor/incarnation 变化拒绝复用）。
3. **崩溃窗口内的重复写入**：B 在 consume 已提交但回执丢失后崩溃，agent 以新
   tool_call_id 重试 → 新审批 → 人工批准 → 可能重复写入。缓解：这是
   计划认可的不确定交付语义（"visible recoverable state"，绝不自动重发）；
   每次执行都有人工决策；审计完整记录；`unknown`/recovery 状态可见。
4. **tmux 键名映射漂移**（协议词表与 node 映射不一致）：缓解：词表钉在
   `termflow_protocol/keys.py`，映射钉在 node，fixture 断言映射覆盖词表全集；
   未知键名两侧 fail closed；映射变更必须同步两个 fixture 测试。
5. **审计表增长**：缓解：90 天 purge（挂入 `purge_expired`）；每行只存元数据
   （有界长度字段）；无原文。
6. **等待占用 binding 并发额度**（2/binding）：缓解：写请求低频；文档明确；
   额度配置可调。

## 决策摘要

- 写工具审批采用**同步等待**（DB 轮询 0.5s），等待超时撤销 pending 并返回
  `approval_required` + approval_id；不做异步 pending + 客户端轮询。
- 执行路径 = 新建 `CommandService`（实现 `TerminalCommandPort`）+ 新
  `CommandGateway` 协议（生产适配器包 `CommandRouter`）；文本走现有
  `send_input`，按键走新增 `CommandRouter.send_keys`。
- typed keys 走**新的 `PANE_KEY_INPUT` 线上消息** + `BridgeHello.typed_keys=True`
  + 共享钉死词表（`termflow_protocol/keys.py`）与 node 侧 tmux 映射；控制字节
  不夹带纯文本路径（计划 §10 约束）。`PaneInputPayload`/`PaneKeyInputPayload`
  增加可选 `pane_incarnation`（agent 路径填充，C 路径不变）。
- canonical hash：`operation="send_text"/"send_keys"`、`encoded_bytes` = 文本
  UTF-8 / 键序列规范编码、`pane_incarnation`+`cursor_precondition` 来自 B 账本、
  `run_id` = 会话当前 running run、`policy_epoch` = 持久化 auth epoch、
  `grant_id=None`；`request_key` 不参与 hash（保持 M5.1 测试向量）。
- settle 规则：确认/已知失败 → `consume`；不确定 → `mark_unknown`；发送先于
  settle，settle CAS 竞争失败时返回事实回执、不改状态；`consumed→unknown` 不存在。
- 执行前重检：auth epoch、expiry、binding 状态、**用当前账本重算 hash**；漂移 →
  `revoke(system:target_changed)`。
- B 重启恢复：`pending → revoked`、`approved → unknown`（并入
  `run_agent_recovery`）；过期清扫扩展覆盖 approved；binding revoked/disabled →
  `revoke_for_binding`。
- 审计：新表 `approval_audit_events` + `ApprovalAuditWriter`（注入
  `ApprovalPolicy`，缺省 no-op）；agent 身份 + 审批上下文 + outcome；90 天保留；
  无原文。
- MCP 接线：注册全部 8 工具；`DEFERRED_WRITE_TOOLS` 清空；handler 级
  `terminal.write` 门槛；`tool_call_id` = SDK `ctx.request_id`；
  `(conversation, tool_call_id)` 唯一约束防重放。
- 错误码：`TermFlowErrorCode` 增加 `APPROVAL_EXPIRED`/`APPROVAL_REVOKED`/
  `APPROVAL_CONFLICT`。
- Delegated Write Grants：零代码路径、`grant_id` 恒 None、能力标志 False 并暴露
  于 capabilities 端点。
- 显示契约：`ApprovalResponse` 增 `pane_id`/`operation`/`intent_summary`；
  `PaneSendTextParams`/`PaneSendKeysParams` 增必填 `conversation_id` 与可选
  `intent`；`PaneWriteResult` 增可空 `approval_id`。
- 人类决策者 actor 保持 `"admin"`（M5.1 既有限制）。
