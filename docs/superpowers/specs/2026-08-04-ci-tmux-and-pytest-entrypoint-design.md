# CI tmux 与 pytest 入口修复设计

## 目标

修复两个已经在 GitHub Actions 中复现的问题，同时保持现有产品和测试边界：

- Node 安装包必须接受满足最低要求的官方 tmux 版本字符串 `tmux 3.2a`。
- Python 工作区测试必须能从仓库根目录导入 `scripts.release.*`。
- 不新增测试文件，不增加测试用例数量；优先让已有测试承担可复用的长期契约。

## 根因

`TmuxRunner` 的版本正则在次版本数字后使用 `\b`。在 `3.2a` 中，`2` 和 `a`
都是单词字符，所以边界不成立，命令虽然以状态码 0 返回，版本仍被误判为不可解析。

仓库使用 pytest 的 `--import-mode=importlib`。直接执行虚拟环境中的 `pytest` 入口时，
仓库根目录不会稳定进入 `sys.path`，因此顶层命名空间包 `scripts` 无法导入；通过同一
Python 解释器执行 `python -m pytest` 时，当前仓库根目录会进入模块搜索路径。

## 方案

### tmux 版本解析

保留最低版本 `(3, 2)` 的比较逻辑，只让解析器接受次版本数字后的 ASCII 字母后缀。
后缀不参与最低版本比较，因此 `3.2a` 与 `3.2` 都满足要求，而 `3.1a` 仍被拒绝。
不放宽到任意字符，避免把不明确的版本文本误判为有效版本。

复用已有的“包装输出或 stderr 版本”参数化测试：将其中一个现有输入替换为
`tmux 3.2a`。这样同一个测试同时永久覆盖包装输出、最低支持版本和官方字母后缀，
测试文件数、测试函数数及参数化用例数均不增长。

### pytest 入口

将 CI 和本地总验证脚本中的 `uv run --all-packages pytest` 改为
`uv run --all-packages python -m pytest`。不修改应用包结构，也不把运维脚本伪装成产品
Python 包。现有 45 个 release 测试直接作为验证，不再添加只检查工作流字符串的重复测试。

## 验证

- 运行现有 `apps/node/tests/test_tmux_runner.py`，确认 `3.2a` 被接受且旧版本仍被拒绝。
- 用模块入口运行现有三个 release 测试文件，确认 `scripts.release.*` 可导入。
- 运行完整 Python 测试集或仓库现有总验证入口，确认没有回归。
- 测试总量不得因为本次修复增加。

## 非目标

- 不降低或提高 tmux 3.2 的最低版本要求。
- 不为 `scripts` 添加 `__init__.py`，不改变其命名空间或发布属性。
- 不新增测试文件、测试函数或参数化用例。
