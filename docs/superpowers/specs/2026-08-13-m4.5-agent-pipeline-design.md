## 目标

- 新增 **`AgentPipelineService`**（每 binding 一个实例）：统一协调 inbox claim、`AgentRunStateMachine`、`OpenCodeAdapter.submit`、SSE 消费循环、`AgentEventCursor` 持久化、`AgentStreamHub` 发布、reconcile 重连。
- 新增 **`AgentRuntimeRegistry`**：binding →（adapter 实例、scope、supervisor 门）的映射，负责 adapter 生命周期（构造/关闭）与 fail-closed 激活。
- 新增 REST **submit 端点** `POST /api/v1/agent/conversations/{conversation_id}/messages`（UserMessage 入口，202 语义）与 **cancel 端点** `POST /api/v1/agent/conversations/{conversation_id}/cancel`。
- WatchTriggered 通过现有 inbox 项自动创建 continuation run 并 submit（无需改动 watches.py 触发事务）。
- SSE 消费循环：`adapter.events()` 的归一化事件 → run 状态机推进 → 持久化 canonical AgentEvent（ephemeral delta 不落库）→ `stream_hub.publish`；流断开后 **bounded backoff reconnect + reconcile**。
- 完成 binding-scoped runtime mapping 接线：binding 的 `runtime_ref`/`runtime_epoch`/`capability_ref` + supervisor `accept_activation` 门 → adapter 构造参数。
- M4.5 测试全部用 fake backend（`httpx.MockTransport` 或内存 fake），真实 OpenCode 容器往返在测试矩阵中标记为 M4 exit。

## 非目标

- 真实 OpenCode 容器集成测试（M4 exit，测试矩阵仅作集成标记；本设计不新增 compose/容器验证）。
- M5 审批：`interact`（permission once/reject）的**产品 API 与 single-use mapping**。M4.5 只把 pipeline 层面的 `resolve_permission()` 传递方法接好（adapter `interact()` 已存在，映射已在 M4.2 测试），REST/approval 接线归 M5。
- 消息正文/事件 payload 的原文持久化：`agent_events`/`agent_messages` 表按现有 schema 只存 digest（`payload_digest`/`body_digest`）；M4.5 沿用该契约（文本经 live hub 传递，C 端历史渲染属 M6）。
- `AgentInboxItem.payload` 原文列：现有 schema 只存 `payload_digest`；M4.5 不新增列。dispatcher 渲染 turn 所需的 typed payload 通过 **in-process 交付**（enqueue 调用点与 pipeline 同进程）解决，并在重启恢复路径 fail-closed（见风险 2）。
- 多个 binding 共享同一 runtime 的适配（plan gate 6 默认 one-runtime-per-binding；`AgentRuntimeRegistry` 按 binding 构造独立 adapter，天然隔离）。
- 定时器（TimerTriggered）、系统通知（SystemNotification）输入路径的产品入口（adapter 已接受这些 kind，但 M4.5 不新增它们的生产者 API）。
- Stream replay（`ReplayMode.NONE`）：reconcile 不重放 SSE，只证明消息状态。
- **B 重启时的会话级 reconcile**（计划 §17 "reconnect OpenCode/SSE and reconcile nonterminal
  sessions/runs"）：M4.5 的 reconcile 循环覆盖 **运行期 SSE 断开**；B 重启后仍沿用现有
  `run_agent_recovery` 的 fence 语义（running → unknown，用户可见可恢复），不自动恢复
  重启前的会话（`context_mode=LOST_ON_RESTART`、`resumable=False` 与之一致）。重启级
  会话恢复若有后续需求，属 M4 exit 或后续里程碑。
- Docker 控制、compose 变更、客户端 contract 生成、Web/Tauri 改动。

## 设计

### 1. 编排结构：`AgentPipelineService`（每 binding 一个实例）

```text
                    AgentRuntimeRegistry (agent/runtime_registry.py)
   binding_id ──►  resolve(binding) ──► OpenCodeAdapter(base_url, directory,
   runtime_ref/epoch/capability_ref          backend_version, runtime_id,
   ── supervisor.accept_activation ──►      binding_capability_epoch)
                                              │
   app.py lifespan ──► AgentPipelineService (agent/pipeline.py, 每 binding 1 个)
     run_agent_recovery 后启动 ──────────────►   ├─ dispatcher loop（claim inbox → submit）
     shutdown 时 stop + adapter.close()          ├─ SSE consumer loop（events() → run SM → cursor）
                                                └─ reconcile/reconnect loop（断开后）
                                                      │
   repositories: agent_inbox / agent_runs / agent_backend_conversations
   AgentEventCursor(agent_events, sessions, publisher=hub.publish)
   AgentStreamHub（live fan-out，已接线于 agent_stream.py）
```

**为什么是一个类而不是分散 hook：** 编排需要共享三类状态——(a) 每 conversation 的 active run 映射（run_id ↔ notification.run_id，dedup 与 run 边界推进需要）；(b) SSE 消费者与 dispatcher 之间的完成信号（run 终态到达后 dispatcher 才能 claim 下一项）；(c) adapter 生命周期与 scope。分散 hook（例如在 watches.py 或 API 里各自 submit）无法在同一个 `asyncio` 任务图里协调这些状态，也会把 run SM 的 CAS 竞态扩散到多个调用点。单个 `AgentPipelineService`（每 binding 实例化）与 plan gate 6（one-runtime-per-binding、same-binding 串行）对齐：串行约束天然落在单实例内部。

```python
class AgentPipelineService:
    """Per-binding orchestration: inbox → adapter → canonical timeline."""

    def __init__(
        self,
        *,
        binding_id: UUID,
        adapter: AgentBackend,
        scope: BackendEventScope,
        capabilities: AgentBackendCapabilities,
        repositories: RepositoryBundle,
        sessions: async_sessionmaker[AsyncSession],
        hub: AgentStreamHub,
        supervisor: SupervisorConnector | None,   # None in unit tests → 门恒开
        runtime_ref: str,
        runtime_epoch: int,
        now: Callable[[], datetime] | None = None,
    ) -> None: ...

    # 生命周期
    async def start(self) -> None          # 启动 dispatcher + SSE consumer 任务
    async def stop(self) -> None           # 取消任务、关闭 adapter

    # 产品入口（由 API 调用）
    async def submit_user_message(self, text: str, *, actor: str) -> SubmitAdmission: ...
    async def cancel_conversation(self, conversation_id: UUID, *, reason: str) -> CancelResult: ...

    # Watch 入口（由 app.py 的 watch deadline 任务调用；enqueue 已由 fire() 完成）
    async def submit_watch_input(self, input: WatchTriggeredInput) -> None: ...

    # 内部循环
    async def _dispatch_loop(self) -> None            # claim inbox → submit
    async def _consume_events(self) -> None           # events() → run SM → cursor
    async def _handle_notification(self, n: BackendNotification) -> None
    async def _reconcile_and_reconnect(self) -> None  # 断开后 bounded backoff + reconcile
```

`AgentRuntimeRegistry`（`agent/runtime_registry.py`）持有 binding → `AgentPipelineService` 的字典，构造/启动/停止/关闭；app.py lifespan 中在 `run_agent_recovery` **之后**启动（恢复先 fence stale runs，再启动 pipeline，避免新提交撞上未回收的 running run）。

### 2. 提交时序（UserMessage）

```text
C/admin  ──POST /api/v1/agent/conversations/{id}/messages──►  agent_conversations.py
   body: {"text": "..."}（plain text，≤64KiB 校验）
   │  1. conversation 存在 + binding 未 revoked/disabled（fail closed）
   │  2. registry.pipeline_for(binding) 不存在 或 supervisor.accept_activation=False
   │     → 503 binding_runtime_unavailable（fail closed，plan §17 "C sees backend unavailable"）
   │  3. pipeline.submit_user_message(text, actor="admin")
   │     ├─ inbox.enqueue(kind=user_message, idempotency_key=uuid4,
   │     │    payload_digest=sha256(text), correlation_id=uuid4, source="user")
   │     │    —— 持久化 admission，204 语义不在此暴露
   │     └─ 内存注册 (inbox_item_id → UserMessageInput/text)，供 dispatcher 渲染
   ▼
   202 Accepted  {"message_id": <inbox_item_id>, "conversation_id", "admission_seq",
                  "idempotency_key", "delivery_state": "pending", "submission_state": "not_started"}
        │
        │  dispatcher loop 轮询（也可由 enqueue 后 set() 事件唤醒）
        ▼
   _dispatch_loop: envelope = inbox_machine.claim_next()
        │ 1. one_active_run(conversation_id) 已由 claim_next 的 in-flight 门保证
        │ 2. payload 查找：内存表 [envelope.id → typed input]
        │    ├─ 命中 → 继续
        │    └─ 未命中 → bounded 宽限重试（如 0.5s × 最多 10 次，等
        │       submit_user_message/submit_watch_input 的注册，消除
        │       fire() 提交与注册之间的进程内竞态窗口）；宽限耗尽（如 B
        │       重启后 payload 永不到达）→ fail-closed：诊断 +
        │       mark_delivery_unknown（见风险 1）
        │ 3. backend_ref = agent_backend_conversations.get_by_conversation()
        │    ├─ None → adapter.create_conversation(CreateBackendConversation(display_title,
        │    │    workspace_alias)) → persist ref（provider_ref 保持 opaque）
        │    └─ 已有 → 复用
        │ 4. run_id = run_machine.create_for_conversation(conversation_id)   # queued
        │ 5. inbox_machine.mark_started(envelope, attempt_id, stable_message_id=idempotency_key,
        │    owner=pipeline_id, fencing_token=...)   # 提交前落盘 claimed→dispatched
        │ 6. 提交前重检 supervisor.accept_activation（epoch 漂移 fail-closed，plan gate 6）
        │ 7. adapter.submit(ref, BackendTurnRequest(
        │      conversation_ref=ref, correlation_id=envelope.correlation_id,
        │      idempotency_key=envelope.idempotency_key,
        │      parts=(BackendTurnPart(kind=USER_MESSAGE, text=text, trust=TRUSTED),),
        │      context=None, disclosure=None, size_policy=..., turn_policy=...))
        ▼
   BackendSubmitResult：
   ├─ confirmed(204) → submission accepted（run 保持 queued，等 SSE RUN_STARTED）
   ├─ retryable(retry_safe=False) → run_machine.fail(error_code="submit_retryable") +
   │     inbox_machine.mark_delivery_unknown（绝不自重试，plan §6.1 step 8 / §7）
   └─ 异常 → 同上 delivery_unknown + run fail（fail-loud 之外的可恢复路径）
```

**in-process payload 关联机制（UserMessage 与 WatchTriggered 共用）：** 由于 inbox 行只持久化
`payload_digest`，typed payload 通过 pipeline 内存表关联：`submit_user_message` /
`submit_watch_input` 在 enqueue/fire 之后把 `(envelope.id → typed input)` 放入
`self._pending_payloads: dict[UUID, AgentInput]`；dispatcher claim 到 envelope 后按
`envelope.id` 取回并渲染 `BackendTurnPart`。单 worker 单进程内无跨进程竞态；B 重启后该表为空，
未 claim 项的渲染 fail-closed 为 delivery_unknown（风险 1 的缓解）。

**204 语义如何暴露：** adapter `submit()` 的 204 → `BackendSubmitResult.confirmed` → `SubmissionStateMachine` → `submission_state=accepted`，产品层**不阻塞等 204**。REST 端点返回 **202 Accepted**（admission 已被持久化），后续状态通过 run/event 时间线观察（`RUN_STARTED` 事件 + conversation 的 run 状态）。204 是适配器内部语义，product API 永不见 204。

### 3. WatchTriggered continuation 路径

watches.py 的 `fire()` 已在触发事务内插入 `AgentInboxItem(kind=watch_triggered)`（M3 完成，`build_watch_triggered_input` 的 continuation JSON 存在 watch 行的 `start_cursor`/`intent_summary`/`proposed_action` 里）。M4.5 需要补两块接线：

**(a) WatchEngine 后台任务启动（app.py lifespan）：** `WatchEngine.rebuild()` → `start()`（订阅 EventHub + 消费循环 + deadline 堆），`check_deadlines(now)` 每 tick 返回 `FiredTrigger` 列表并调用 `fire()`；`stop()` 在 shutdown。此接线是计划 955 行 "watch lifecycle tasks land in M2-M4" 的收尾。

**(b) FiredTrigger → pipeline 交付（trigger sink 端口，review 修正 M1）：**

```text
WatchEngine.check_deadlines / evaluate_live_event ──► fire() ──► FiredTrigger + WatchDelivery + AgentInboxItem
        │
        ▼  (WatchEngine 的 on_fired trigger sink；app.py 接线到 runtime registry)
   input = engine.build_input(trigger, observed_at=now)     # WatchTriggeredInput（内存）
   pipeline = registry.pipeline_for(trigger.watch.binding_id)
   await pipeline.submit_watch_input(input)                 # 内部 enqueue 已由 fire() 完成，
                                                            # 只做渲染 + dispatcher 唤醒
        ▼
   _dispatch_loop 渲染 turn：
   parts = (BackendTurnPart(
       kind=WATCH_TRIGGERED,
       text=<continuation 文本>,
       trust=UNTRUSTED),)          # 计划 §6: terminal observation 显式 untrusted
```

**in-process 交付：** inbox 行只有 `payload_digest`，因此 dispatcher 无法从 DB 重建 typed payload。设计为：`WatchEngine` 构造新增 `on_fired` trigger sink 回调端口（live 触发路径与 deadline 路径的每个 `FiredTrigger` 都经 sink 交付；`fire()` 仍只负责触发事务内插入 inbox 行 + delivery，sink 负责 `engine.build_input(trigger, observed_at=...)` → `pipeline.submit_watch_input(input)` 注册 typed payload，存入 `_pending_payloads[envelope.id]`，与 §2 的 UserMessage 走同一机制）。同一进程内交付，单 worker SQLite 无跨进程竞态；`fire()` 提交与 sink 注册之间的竞态由 dispatcher 的 bounded 宽限重试消除（§2 步骤 2）。B 重启后未 claim 的 watch inbox 项没有内存 payload → dispatcher **跳过 claim 保持 pending**（记诊断），绝不 `mark_delivery_unknown` 烧毁 continuation；`recover_stale` 恢复为 pending 后保持可见（见风险 1 的缓解）。这符合计划 §7 "uncertain delivery is a visible recoverable state"，且不引入 schema 改动。

### 4. SSE 消费循环

`_consume_events` 每 binding 一条任务：

```text
async for notification in adapter.events(scope):     # scope: BackendEventScope(binding_id, runtime_epoch)
  │
  ├─ 1. 归属校验：notification.scope.binding_id == self.binding_id 且
  │      notification.conversation_ref.runtime_id == self.adapter.runtime_id
  │      → 不匹配：丢弃 + 计数（诊断），绝不路由到别的 conversation（M0 契约）
  ├─ 2. conversation 解析：agent_backend_conversations.get_by_provider_ref(
  │      notification.conversation_ref.provider_ref)
  │      → 无行（会话已删/未知）→ 丢弃 + 诊断
  ├─ 3. run 映射：active_run = 该 conversation 当前 queued/running 的 run
  │      → 无 active run → 丢弃 + 诊断（陌生会话事件，M0 scoped-subscription 拒绝；
  │        重启后 recovery 已把 stuck running fence 为 unknown，旧会话事件同样丢弃，
  │        由 reconcile 路径（§5）处理状态证明，不臆断完成）
  │      → 有 → notification.run_id（UUID5）作为 backend_run_id 关联（plan §6.1 step 7）
  ├─ 4. run 状态机（infer_run_boundary(capabilities, notification)）：
  │      RUN_STARTED  → run_machine.start(run_id, backend_run_id=str(notification.run_id))
  │      RUN_COMPLETED→ run_machine.complete(run_id)
  │      RUN_FAILED   → run_machine.fail(run_id, error_code=payload.error_code or "run_failed")
  │      （explicit_run_boundaries=True：只信显式边界事件；start 失败若 run 已 running → 幂等忽略）
  ├─ 5. canonical AgentEvent 持久化（先持久化后 fan-out，plan §4.4）：
  │      AgentEventCursor.append(
  │          conversation_id=..., event_kind=notification.kind.value,
  │          dedup_key=notification.dedup_key,          # repository 原子 dedup
  │          payload_digest=sha256(canonical payload json),
  │          run_id=run_id, ephemeral=(kind == MESSAGE_DELTA))
  │      → cursor 内部 publisher=hub.publish 完成 live fan-out
  └─ 6. message 装配（durable 才落库）：
         MESSAGE_COMPLETED → AgentMessageRepository.create(
             conversation_id, role="assistant", kind="text",
             body_digest=sha256(payload.text), run_id=run_id, is_final=True)
         MESSAGE_DELTA → 仅 ephemeral 事件，不落 agent_messages（plan §4.4）
         TOOL_STARTED/COMPLETED、PERMISSION_REQUESTED、RUN_* → 仅事件行（durable）
```

异常语义：`events()` 是非 200/连接失败时**干净结束**的迭代器（M4.2 已保证），所以 `async for` 正常退出即触发 reconcile 循环；`CancelledError`（shutdown）直接传播。

### 5. 断开/重连 reconcile（计划 §6.1 step 6-8）

```text
events() 迭代结束（非 shutdown）
   │
   ▼
_reconcile_and_reconnect():
   for conversation in binding 下所有有 backend_ref 且 run 非终态 的 conversation:
       snapshot = adapter.reconcile(ref)            # GET /session/:id/message（bounded limit）
       │
       ├─ outcome == CONFIRMED  → run 保持 running；submission 视为 accepted；
       │     若 snapshot.message_count 与上次已处理数一致且无新事件 → 继续等（不臆断完成）
       ├─ outcome == CONTEXT_LOST（404）→ run_machine.fail(error_code="context_lost")
       │     + inbox mark_delivery_unknown（SubmissionStateMachine: context_lost→unknown）
       └─ outcome == UNKNOWN（网络失败）→ 指数退避重试 reconcile（1s/2s/4s/.../cap 30s，
            上限 N 次，默认 5 次）；耗尽 → run_machine.mark_unknown + inbox
            mark_delivery_unknown（绝不自重试，plan §6.1 step 8）
   │
   ▼
   重新订阅 adapter.events(scope)（bounded backoff 重连，cap 30s，持续重试直到 stop()）
```

**run mark_unknown 时机汇总**（计划 §7 与 §17 对齐）：

| 场景 | run 处置 | inbox 处置 |
|---|---|---|
| submit confirmed（204） | queued（等 RUN_STARTED） | dispatched/accepted |
| submit retryable / 连接失败 | fail(error_code=submit_retryable) | delivery_unknown（parked） |
| RUN_STARTED 到达 | running（记 backend_run_id） | 不变 |
| RUN_COMPLETED / RUN_FAILED 到达 | completed / failed | 不变 |
| SSE 断开 + reconcile CONFIRMED | 保持 running（重连后继续） | 不变 |
| SSE 断开 + reconcile CONTEXT_LOST | fail(error_code=context_lost) | delivery_unknown |
| SSE 断开 + reconcile UNKNOWN（重试耗尽） | mark_unknown | delivery_unknown |
| B 重启（run_agent_recovery，已存在） | running → unknown | recover_stale 恢复/unknown |
| cancel confirmed 但无终态事件 | cancel（见 §8） | dispatched |

### 7. 并发与序列化（plan gate 6、plan §7 "one in-flight turn per conversation"）

- **每 conversation 一个 in-flight**：由 `InboxDeliveryStateMachine.claim_next`（`max_in_flight_per_conversation=1`，OpenCode `concurrency_mode=SERIALIZED`）保证——第二个 UserMessage 在同一 conversation 的 run 完成前保持 pending。
- **每 binding 串行**：`AgentPipelineService` 每 binding 单实例，其 dispatcher 每次只处理一个 envelope（claim → submit → 等 run 终态信号再 claim 下一个）。第二个 conversation 的 inbox 项在 DB 中等待（plan §6.2.1 "A second conversation waits in the Inbox"）。
- **one_active_run 双重保险**：dispatcher 提交前调用 `run_machine.one_active_run(conversation_id)`（若 recovery 遗留 running run，拒绝新提交并回退等待），SSE 消费循环的 `run.start` 失败（run 已非 queued）幂等忽略。
- **binding 级恢复顺序**：app.py lifespan 中 `run_agent_recovery()`（fence stale runs）→ `AgentRuntimeRegistry.start_all()`（每 binding 一个 pipeline）→ dispatcher 才 claim。顺序保证新提交不会与未知状态 run 并发。

### 8. cancel / interact 传递

- **cancel**：`POST /api/v1/agent/conversations/{conversation_id}/cancel` →
  1. 找 active run（running/queued）；无 → 409 `no_active_run`。
  2. `adapter.cancel(BackendCancelRequest(conversation_ref, run_id, correlation_id, reason))`：
     - `confirmed`（2xx）→ run 保持，等终态事件；若 `cancel_scope=CONVERSATION`（abort 整个 session）后 **bounded 等待**（如 5s）仍无 `RUN_FAILED`/`RUN_COMPLETED` → reconcile：session 已无活动 → `run_machine.cancel()`；仍 busy → `mark_unknown`（计划 §7：cancel 后必须等终态事件或 reconcile，不确定则 unknown）。
     - `unknown`（连接失败）→ `run_machine.mark_unknown`（绝不在不确定时臆断 cancelled）。
  3. 响应 `202 {"outcome": "confirmed"|"unknown", "run_state": ...}`。
- **interact（permission once/reject）**：M4.5 只在 pipeline 暴露 `async def resolve_permission(self, interaction: BackendInteraction) -> BackendOperationResult`，内部转发 `adapter.interact`（`approved→"once"`、`denied→"reject"`，M4.2 已测）。**无产品 API**；M5 的 ApprovalRequest → `permission_ref` single-use mapping 接入该方法的 REST 层归 M5（本设计非目标明确写出）。

## 安全

- **绑定/运行时隔离**：每个 notification 校验 `scope.binding_id` 与 `conversation_ref.runtime_id`；不匹配事件丢弃并计数（M0 scoped-subscription 契约延续）。`AgentRuntimeRegistry` 每 binding 独立 adapter；第二个 binding 无 runtime → 503 fail-closed（plan §6.2.1）。
- **fail-closed 提交**：binding revoked/disabled、runtime 未 ready、adapter submit 非 204 均不产生"已接受"假象；`retry_safe=False` 的 retryable/unknown 绝不自重试（计划 §6.1 step 8 的 no-silent-duplicate-action）。
- **Opaque refs**：产品 API 永不暴露 `provider_ref`/runtime_id/backend_kind；`BackendConversationRef` 保持 opaque（M0 契约，测试 `test_product_endpoints_never_expose_backend_internals` 延续）。
- **payload 边界**：写入 `agent_events`/`agent_messages` 的只有 digest；文本经 live hub 传递，不落库（与现有 schema/§16.1 保留矩阵一致）。
- **权限传递**：`interact` 仅 `once`/`reject`（M4.2 `_permission_response_body` fail-closed）；无产品端点，M5 才引入审批面。
- **诊断脱敏**：reconcile 失败/丢弃事件只记 bounded 诊断（identifier + reason），不记 provider payload/headers（M4.2 `OpenCodeSseDiagnostic` 模式延续）。

## 风险与缓解

1. **in-process payload 交付在 B 重启后丢失**（inbox 只有 payload_digest，无法从 DB 重建 typed payload）：未 claim 的 watch/user 项重启后无法渲染。缓解：dispatcher 对无法渲染的项 fail-closed——记 bounded 诊断 + `mark_delivery_unknown`（可见、可恢复，符合计划 §6.1 step 8 "uncertain delivery is a visible recoverable state"）；已 `mark_started` 的项由 `recover_stale` 正确恢复为 delivery_unknown 且绝不自动重试；进程内 `fire()` 提交与 `submit_watch_input` 注册之间的竞态由 bounded 宽限重试消除。若后续需要完全重启安全，可加 inbox payload 列（独立小迁移，非 M4.5 范围）。
2. **SSE 断开窗口内的事件丢失**（`ReplayMode.NONE`，reconnect 不重放）：若断开期间后端完成了 run，重连后收不到 `RUN_COMPLETED`，run 会停留在 running。缓解：reconcile 证明会话状态（CONFIRMED 且 message_count 停滞）；`run.mark_unknown` 只在 reconcile 无法证明时触发（UNKNOWN 重试耗尽/context_lost），绝不臆断 completed/failed；产品端通过事件时间线看到 run 状态并人工决策（计划 §7 的 visible recoverable state）。
3. **cancel 后无终态事件**（abort 是 conversation 级，可能不产生 run_failed 事件）：缓解：bounded 等待 + reconcile 证明（session 已无活动 → cancel；仍 busy → mark_unknown）；绝不在 `adapter.cancel` 返回 unknown 时臆断 cancelled（计划 §7 明确要求）。
4. **多个 binding 并发编排的复杂度**：每 binding 一个独立 pipeline 实例（独立 adapter/scope/任务图），互不共享可变状态；registry 只做构造/启停，不做跨 binding 调度。
5. **fake backend 与真实容器差异**：M4.5 全部断言建立在 fake（MockTransport/内存 fake）上，真实容器语义（重连窗口、abort 行为、permission 事件时序）可能有偏差。缓解：测试矩阵把真实容器项显式标记为 M4 exit 集成验证，且 fake 严格按 pin（`opencode-pin.md`）行为建模（204、非 200、404、SSE 干净结束）。
6. **dispatcher 与 SSE consumer 的完成信号竞态**：run 终态事件先于 `mark_started` 完成到达（罕见）→ run 未找到而丢弃事件。缓解：`_handle_notification` 对"无 active run"事件先查 `agent_runs.list_for_conversation` 最新行（按 started_at 倒序），若已有终态行则视为已处理（dedup 键防重复），否则丢弃并计诊断。
7. **正式偏差声明（M4.5 code review M2）：supervisor 门未接线**。`AgentRuntimeSupervisor` 端口在当前全库仍是 `_unimplemented_port` 占位符；M4.5 生产 composition root 以 `supervisor=None` 构建 `AgentRuntimeRegistry`，activation 门因此**暂时恒开**（`accept_activation` 为 no-op 语义）。风险面：runtime 就绪性/epoch 漂移的生产级拒绝（quiesce/attestation）留待 supervisor 端口落地时接线；M4.5 仍保持的 fail-closed 面是：binding 缺 `runtime_ref`/`runtime_epoch` 字段一律拒绝激活（`RuntimeNotReadyError` → 503）。**留后续任务标记**：`AgentRuntimeSupervisor` 端口落地时，composition root 必须注入真实 `SupervisorConnector` 并移除本偏差声明。

## 决策摘要

- 编排采用**每 binding 一个 `AgentPipelineService` 实例**（`agent/pipeline.py`），内部含 dispatcher 循环、SSE 消费循环、reconcile 重连循环；不采用分散 hook。理由：共享 run 映射/完成信号/adapter 生命周期需要单一任务图，且与 plan gate 6 的 binding 串行模型对齐。
- **`AgentRuntimeRegistry`**（`agent/runtime_registry.py`）负责 binding → adapter（base_url/directory/runtime_id/binding_capability_epoch）+ supervisor `accept_activation` fail-closed 门；adapter 每 binding 独立实例。**偏差（见风险 7）**：supervisor 门随 `AgentRuntimeSupervisor` 端口落地接线，M4.5 生产暂时恒开；binding 缺 runtime 字段仍 fail-closed。
- submit 端点：`POST /api/v1/agent/conversations/{conversation_id}/messages`，**202 Accepted**（admission 持久化即返回）；204 是 adapter 内部语义（→ `submission_state=accepted`），产品经 run/event 时间线观察。
- WatchTriggered：复用现有 fire() 触发事务 + dispatcher 统一 claim；turn part `trust=UNTRUSTED`；payload 通过 in-process 交付（watch engine 的 `on_fired` trigger sink → `submit_watch_input`），重启后无 payload 的 watch 项跳过 claim 保持 pending（不烧毁为 delivery_unknown）。
- SSE 消费：归属校验（binding_id/runtime_id）→ conversation 解析 → run 状态机（显式边界事件）→ `AgentEventCursor.append`（ephemeral=delta）→ 先持久化后 fan-out；`MESSAGE_COMPLETED` 落 `agent_messages`（digest-only）。
- 断开恢复：reconcile 三态映射（CONFIRMED 保持/CONTEXT_LOST fail/UNKNOWN 退避后 mark_unknown）+ bounded backoff 重连；**绝不自重试**（retry_safe=False）。
- 并发：inbox SM 每 conversation 1 in-flight + 每 binding 单 pipeline 串行 + `one_active_run` 双重保险；恢复顺序 `run_agent_recovery` → `start_all`。
- cancel：adapter.cancel + 等终态/reconcile 后 `cancel()`/`mark_unknown`；API 202 + 409 无 active run。
- interact：仅 pipeline 方法 `resolve_permission`（once/reject 转发），无产品 API（M5 接线）。
- 零 schema 迁移、既有已审查模块零改动（opencode/runs 只被消费；watches/inbox 仅新增最小回调端口）；新增 settings 均有默认值。
